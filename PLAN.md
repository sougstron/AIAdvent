# План: управление форматом и длиной ответа LLM (TASK-003)

Расширяем `ask` тремя уровнями контроля ответа: **формат (JSON)**, **лимит длины**,
**stop sequence** — с переключалками режимов и сравнением «с ограничениями / без».

---

## 0. Что показала разведка API (сделано, влияет на весь план)

Прогнал живые запросы к `yolo-auto.com/v1`, модель `qwen3.8-27b`. Четыре факта,
которые меняют наивную реализацию:

| # | Факт | Следствие для кода |
|---|---|---|
| 1 | `response_format: {type:"json_schema", strict:true}` **поддерживается** и возвращает чистый JSON по схеме | Основной режим `--format schema` строим на нём, а не на промпт-инжиниринге |
| 2 | Модель **reasoning-типа**: по умолчанию отдаёт `reasoning_content` и тратит `reasoning_tokens` | Нужен отдельный тумблер «мышление вкл/выкл» |
| 3 | `max_tokens` **считает и reasoning-токены**. При `max_tokens: 40` весь бюджет съело мышление: `finish_reason: "length"`, а `content` пришёл **`null`** | Текущий `Message { content: String }` на этом **упадёт** — обязателен `Option<String>` |
| 4 | `stop` применяется **и к потоку reasoning**. `stop: ["}"]` матчнулся внутри размышления, генерация оборвалась на 17 токенах, `content: null` | Stop sequence корректно работает только при выключенном мышлении |

Мышление отключается двумя способами, оба проверены и дают `reasoning_tokens: 0`:
`reasoning_effort: "none"` либо `chat_template_kwargs: {enable_thinking: false}`.

**Главный вывод:** «чёткий одинаковый JSON вне зависимости от количества запросов»
достигается связкой **json_schema + strict + выключенное мышление**, и только тогда
лимит длины и stop sequence становятся предсказуемыми. Это и есть основной сюжет
демонстрации.

## 1. Целевой CLI-интерфейс

```
ask [OPTIONS] <вопрос...>

Формат ответа:
  --format <text|json|schema>   text = как сейчас; json = json_object;
                                schema = строгая json_schema (по умолчанию для темы)
  --topic <name>                тема/схема: weather, gamedev, ...
  --schema-file <path>          своя JSON-схема вместо встроенной

Длина:
  --max-tokens <N>              лимит бюджета генерации
  --max-items <N>               «мягкий» лимит — через схему (maxItems), а не токены

Завершение:
  --stop <SEQ>                  можно повторять, до 4 штук

Мышление:
  --think <on|off>              off => reasoning_effort=none (по умолчанию off)

Сравнение и вывод:
  --runs <N>                    повторить запрос N раз
  --compare                     прогнать матрицу режимов и вывести отчёт стабильности
  --raw                         показать полный ответ API (usage, finish_reason)
  --tui                         интерактивный экран настроек
```

Все флаги дублируются переменными окружения (в стиле существующих `YOLO_*`),
чтобы TUI и CLI делили одну конфигурацию.

## 2. Режимы (то, что переключаем)

Конфиг — одна структура `RunConfig`, которую одинаково собирают CLI-парсер, env и TUI:

```rust
struct RunConfig {
    format: Format,          // Text | JsonObject | JsonSchema(SchemaRef)
    max_tokens: Option<u32>,
    stop: Vec<String>,
    thinking: bool,
    runs: u32,
}
```

Пресеты для быстрого переключения:

| Пресет | format | max_tokens | stop | think | Ожидаемое поведение |
|---|---|---|---|---|---|
| `baseline` | text | — | — | on | Свободный текст, разный каждый раз |
| `json-soft` | json_object | — | — | on | JSON, но ключи «плавают» от запуска к запуску |
| `strict` | json_schema | — | — | off | Идентичный набор ключей и типов на всех прогонах |
| `capped` | json_schema | 300 | — | off | Проверка обрыва по длине + `finish_reason: length` |
| `stopped` | text | 500 | `["\n---\n"]` | off | Обрыв ровно на разделителе |
| `strict+all` | json_schema | 400 | `["\n\n"]` | off | Все три ограничения вместе |

## 3. Эксперимент «с ограничениями vs без»

Это отдельная команда `--compare`, а не ручное сравнение глазами. Для каждого пресета
делаем `--runs N` (по умолчанию 5) и считаем метрики:

- **JSON-валидность** — доля прогонов, где ответ распарсился (`N/N`)
- **Совпадение схемы** — доля, прошедшая валидацию по целевой схеме
- **Стабильность ключей** — хэш отсортированного набора путей JSON; сколько различных вариантов на N прогонов (идеал: 1)
- **Стабильность типов** — совпадают ли типы значений по одинаковым путям
- **Длина** — min/median/max `completion_tokens`, разброс
- **`finish_reason`** — распределение `stop` / `length`
- **Стоимость** — суммарные токены, отдельно reasoning

Вывод — таблица «пресет × метрика» плюс сохранение сырых ответов в
`runs/<timestamp>/<preset>-<i>.json` для отчёта. Это прямо закрывает
«нужно сравнить результаты с ограничениями и без».

## 4. TUI

`ratatui` + `crossterm`, один экран:

- слева — список настроек (стрелки/`Tab` переключают, `Space` тоглит, цифры задают числа)
- сверху — строка пресета, `p` циклит пресеты
- `Enter` — выполнить, `c` — запустить `--compare`
- справа — две панели: последний ответ и метрики/`usage`/`finish_reason`
- `s` — сохранить текущий конфиг, `q` — выход

TUI не содержит логики: собирает тот же `RunConfig` и зовёт тот же `run()`, что и CLI.

## 5. Структура кода

Разносим сегодняшний единственный `main.rs` (123 строки) на модули:

```
src/
  main.rs        точка входа, диспетчер CLI vs TUI
  cli.rs         разбор аргументов и env -> RunConfig
  config.rs      RunConfig, Format, пресеты
  api.rs         сборка тела запроса, вызов, разбор ответа
  topics.rs      реестр тем: имя -> JSON-схема + системный промпт
  compare.rs     прогоны, метрики, отчёт
  tui.rs         интерактивный экран
schemas/         .json схемы тем (встраиваем через include_str!)
```

Зависимости к добавлению: `ratatui`, `crossterm`, `jsonschema` (валидация),
`clap` (разбор флагов — иначе ручной парсер разрастётся).

## 6. Этапы

1. **Фундамент** — `Option<String>` для `content`, чтение `finish_reason` и `usage`, разбиение на модули, `clap`. Здесь же чинится реальный баг из п.0.3.
2. **Формат** — `--format`, реестр тем в `topics.rs`, одна схема выбранной темы, `--raw`.
3. **Длина и stop** — `--max-tokens`, `--stop`, `--think`, честная обработка обрыва (`finish_reason: length` => предупреждение, а не тихий мусор).
4. **Сравнение** — `--runs`, `--compare`, метрики, сохранение прогонов.
5. **TUI** — экран настроек поверх готового ядра.
6. **Отчёт** — прогнать матрицу на выбранной теме, положить таблицу результатов в README.

Этапы 1–4 дают полную функциональность из задания; 5 — «можно собрать простейший
интерфейс», то есть приятный, но отделяемый бонус.

## 7. Риски

- **Reasoning ломает лимиты** (п.0.2–0.4) — снимается тумблером `--think off` по умолчанию; в отчёте показываем оба варианта, это хороший материал для сравнения.
- **Обрыв по `max_tokens` даёт невалидный JSON** — ожидаемое поведение, но нужно явно отличать «модель не смогла» от «мы обрезали»; для этого и читаем `finish_reason`.
- **`--max-items` через схему надёжнее токенного лимита** для ограничения объёма списков — токены режут посреди слова, `maxItems` режёт по смыслу. Стоит показать оба.
- **Провайдер может игнорировать часть параметров** на других моделях — `--raw` позволяет это увидеть.

## 8. Десять тем на выбор

Хорошая тема здесь = стабильная вложенная схема + **список повторяющихся элементов**
(на нём наглядно работают и лимит длины, и stop sequence) + понятный «сервис».

| # | Тема | Ядро схемы | Чем хороша для демонстрации |
|---|---|---|---|
| 1 | **Дайджест геймдев-новостей** | `{period, items[{title, studio, platform[], category, date, summary, hype_score}]}` | Идея из задания. Список ⇒ `maxItems` и stop по разделителю между новостями; `hype_score` — числовой enum-контроль |
| 2 | **Погода по региону за X времени** | `{region, from, to, days[{date, t_min, t_max, condition, precip_mm}], summary}` | Идея из задания. Жёсткие типы (числа, даты, enum условий) — идеальный тест «одинаковый JSON на N прогонах» |
| 3 | **Карточка релиза OSS-проекта** | `{repo, version, date, breaking[], features[], fixes[], upgrade_notes}` | Три параллельных списка — видно, как лимит длины «съедает» хвост; stop на `## ` естественен |
| 4 | **Сводка по вакансиям** | `{query, vacancies[{title, company, grade, stack[], salary{min,max,currency}, remote}]}` | Вложенный объект + enum грейда; хорошо ловит «плавающие ключи» в json_object без схемы |
| 5 | **Финансовый брифинг дня** | `{date, assets[{ticker, price, change_pct, trend}], market_mood, top_event}` | Строгие числа и enum тренда — самый чувствительный к типовой нестабильности вариант |
| 6 | **Рецепт из имеющихся продуктов** | `{dish, servings, time_min, ingredients[{name, qty, unit}], steps[]}` | `steps[]` — длинный список, показательно для `max_tokens` и stop по номеру шага |
| 7 | **План дня в городе** | `{city, date, blocks[{time, place, kind, duration_min, cost}], total_cost}` | Есть агрегат (`total_cost`) — видно, ломается ли согласованность при обрыве |
| 8 | **Карточка фильма/сериала под настроение** | `{mood, picks[{title, year, genre[], runtime_min, why, rating}]}` | Компактно, дёшево гонять по 20 прогонов для статистики стабильности |
| 9 | **Флешкарты для изучения языка** | `{lang, level, cards[{front, back, example, tags[]}]}` | Однородные повторяющиеся элементы — эталонный кейс для stop sequence «дай ровно N карточек» |
| 10 | **Структурирование инцидента (постмортем)** | `{severity, timeline[{ts, event}], root_cause, impact, action_items[]}` | Самая «взрослая» схема: enum severity + временная шкала; хорошо показывает ценность strict-режима |

**Рекомендация:** взять **#2 (погода по региону за X времени)** как основную. Она прямо
названа в задании, у неё самая типово-строгая схема (числа, даты, enum), а значит
разница между `text` / `json_object` / `json_schema` будет видна нагляднее всего —
именно там «плавающий» ответ ломается заметнее, чем в текстовых полях.
Вторым кандидатом — **#1 (геймдев-новости)**, если хочется более живого контента.

Отмечу: тема тут — сменный плагин (`topics.rs` + файл схемы), так что выбор не
блокирует этапы 1 и 3–5 и при желании меняется позже одной строкой.
