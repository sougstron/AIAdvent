# Почему home-server медленный и что с этим делать (TASK-120, 2026-10-11)

Ревью задач 26–30 после TASK-118. Ничего в работающем движке не менялось.
Все цифры ниже получены вживую на сервере. Это одиночные прогоны, не SLA.

## Диагноз: проблема в движке и ресурсах, а не в размере модели

Сервер почти простаивает: load 0.15 при 16 потоках. Ollama 0.13.5 работает
на AVX2-бэкенде (`libggml-cpu-haswell.so`) с `NumThreads:4` при квоте
3.70 CPU. Из-за этого cgroup троттлится в **11561 из 12967** периодов (89%).

Замер через Ollama (`ollama run --verbose`, `qwen3:0.6b`, промпт на 2124 токена):
prefill **97.6 tok/s**, decode **27 tok/s**. Стартовый промпт приложения
занимает 4.6k токенов. Отсюда и минуты до первого слова.

У Radeon 680M есть **4096 MiB VRAM, зарезервированных в BIOS** (UMA carve-out).
Занято из них 15 MiB. Эта память уже вычтена из 19.7 GiB хоста, поэтому её
использование не отнимает RAM у VM/CT. В образе Ollama даже есть
Vulkan-бэкенд, но он не включён. `/dev/dri/renderD128` уже открыт для CT102
(media). Совместное использование render node для compute допустимо.

## Замер: llama.cpp `llama-bench`, те же GGUF-файлы, промпт 4096 токенов

Образ `ghcr.io/ggml-org/llama.cpp:full-vulkan` (build 23b0202a1), одноразовый
контейнер `--rm` с лимитом 3 GiB. В режиме «CPU» устройство GPU в контейнер
не пробрасывалось (`ngl -1`).

| Вариант | 0.6B prefill | 0.6B decode | 1.7B prefill | 1.7B decode | TTFT на 4.6k (1.7B) |
|---|--:|--:|--:|--:|--:|
| Ollama, как сейчас (4 потока, 3.7 CPU) | ~98 | 27 | ~28 (по README) | — | 160–200 s |
| llama.cpp CPU, 4 потока, 3.7 CPU | 199 | 72 | 101 | 28 | ~46 s |
| llama.cpp CPU, 8 потоков, 8 CPU | 336 | 75 | 174 | 31 | ~27 s |
| **llama.cpp Vulkan 680M, `-ngl 99`** | **1112** | **88** | **663** | **36** | **~7 s** |

Все значения в tok/s. Выводы:

- При тех же 4 потоках llama.cpp уже в 2–2.5 раза быстрее Ollama.
- Добавить CPU-ядер помогает слабо, примерно в 1.7 раза.
- iGPU ускоряет prefill в 6–7 раз и почти не занимает CPU (2 потока).
  На 1.7B получается примерно 7 s вместо ~3 минут. 0.6B для скорости
  становится не нужна.

## Предложение

**1. Движок: заменить Ollama на `llama-server` (llama.cpp) с Vulkan на 680M.**
Две лёгкие службы в том же compose-проекте `ask-home-engine`:
- чат: `qwen3:1.7b`, `-ngl 99 -c 8192 -fa on --jinja`, с thinking off через шаблон;
- embeddings: `nomic-embed-text`, `--embeddings`.

Существующие GGUF-блобы из `models/blobs` переиспользуются, качать ничего не
нужно. Шлюз `gateway.py` остаётся (ключи, лимиты, 429). Меняется только
backend-адаптер на `/v1/chat/completions` и `/v1/embeddings` llama-server.
Контракт для приложения не меняется. Бонусом появляется **настоящий потоковый
SSE**, вместо нынешней буферизации. Модели (1.26 GiB + KV 8k + 0.27 GiB)
помещаются в 4 GiB VRAM. RAM-лимит контейнеров можно опустить ниже нынешних
4 GiB.

**2. Модель: вернуть 1.7B.** Опционально — A/B с `qwen3:4b` Q4_K_M
(~2.5 GiB; по VRAM влезает впритык, нужен отдельный замер). 0.6B не держит
контракт инвариантов, а со скоростью на GPU её единственный плюс пропадает.

**3. «Наш local llm server».** Бинарники из `~/Github/local` собраны под
CUDA/RTX 4070 и Zen 4 (`GGML_NATIVE`, AVX-512). На сервере нет ни NVIDIA,
ни AVX-512, так что напрямую они не запустятся. Брать стоит тот же движок
(mainline llama.cpp / `llama-server`), но в официальной Vulkan-сборке с
закреплённым digest. Из `opt/ornith` можно перенять идею preflight-проверок
и профилей. ik_llama.cpp здесь не нужен: его преимущество — CPU/MoE-ядра,
а узкое место закрывает iGPU.

**4. «Выделить больше ресурсов».** Для CPU-варианта это лишь 1.7 раза
(8 потоков). Имеет смысл только как fallback, если GPU недоступен.
Мелкий фикс при любом варианте: число потоков должно быть не больше квоты
(сейчас 4 потока при 3.7 CPU, отсюда троттлинг 89%).

**5. Приложение (отдельно, без изменения defaults).** Стартовые 4.6k токенов —
это `AGENTS.md` с историей тасок. Даже на GPU короткие актуальные правила
сэкономят несколько секунд на каждом холодном запросе.

## Как проверить результат («проверить инференс с сервера»)

Скриптовый прогон против шлюза с реальными ключами. Принимается только
причинная подпись, а не «текст изменился»:

1. `ask --verify-login`: оба API, модель эхом, 768-мерный вектор.
2. TTFT, prefill и decode tok/s на реальном стартовом промпте приложения
   (4.6k) и на коротком. Сравнение с таблицей выше, `finish_reason` и
   usage-токены из ответа.
3. Качество: прогон RAG-вопросов `docs/questions.json` через
   `--rag-provider home-server` для 1.7B (и 4B при A/B). Сравнение
   доли верных ответов и прохождения инвариантов с 0.6B.
4. `ollama ps`/`nvtop`-эквивалент: `mem_info_vram_used` растёт, CPU контейнера
   остаётся низким. Это доказывает, что работает именно GPU.
5. Живой TUI-смоук (tmux): первый ответ за секунды, текст идёт потоком.

Откат: `control.sh stop` нового варианта и старый compose с Ollama.
Модели и ключи не трогаются.

Временный образ `ghcr.io/ggml-org/llama.cpp:full-vulkan` (3.59 GB) оставлен
на сервере для этого плана. Удалить его можно командой
`docker image rm ghcr.io/ggml-org/llama.cpp:full-vulkan`.
