- **Запрос:** Объясни разницу между HTTP-кэшированием по ETag и по Last-Modified: когда какой выбрать и какие ошибки чаще всего допускают. До 200 слов.

## Ответы

### слабая — `qwen3.8-27b`

<sub>1051 ток., 26.0 с, finish_reason: `stop`, слов: 142, уникальных: 75%</sub>

> **Last-Modified** — метка времени (точность до секунды). Клиент шлёт `If-Modified-Since`; сервер отвечает 304, если файл не менялся после этой даты.
> 
> **ETag** — строковый идентификатор (хеш содержимого, версия). Клиент шлёт `If-None-Match`; сервер сравнивает и отдаёт 304 при совпадении. Бывает сильный (`"abc"`) и слабый (`W/"abc"`).
> 
> **Когда что:**
> - **ETag** — нужна точность: правки внутри одной секунды, контент меняется без смены mtime, CDN/распределённые системы, где mtime ненадёжен.
> - **Last-Modified** — простые статические файлы с корректным mtime; заголовок короче.
> - **Лучшая практика:** отправлять оба заголовка; клиент приоритизирует ETag.
> 
> **Частые ошибки:**
> 1. Генерировать ETag из mtime — сводит преимущество на нет.
> 2. Полагаться только на Last-Modified для файлов, обновляемых чаще раза в секунду.
> 3. Не обрабатывать 304 на клиенте (повторно парсить пустое тело).
> 4. Ставить сильный ETag на динамический HTML с микровариациями — нужен слабый `W/`.
> 5. Не инвалидировать кэш, когда контент сменился, а mtime остался прежним.


### средняя — `grok-4.6`

<sub>742 ток., 16.0 с, finish_reason: `stop`, слов: 110, уникальных: 79%</sub>

> **Last-Modified** — валидация по времени. Клиент шлёт `If-Modified-Since`; сервер отвечает 304, если ресурс не новее. Точность обычно до секунды.
> 
> **ETag** — метка версии (хеш, ревизия). Клиент шлёт `If-None-Match`. Ловит любое изменение содержимого, даже без смены mtime.
> 
> **Когда что:** Last-Modified — дешёвая статика с надёжным mtime. ETag — динамика, несколько серверов/CDN, content negotiation, когда время врёт или недостаточно.
> 
> **Типичные ошибки:** ETag от inode/mtime без содержимого → ложные 304; разные ETag на репликах; слабый ETag при Range; Last-Modified и рассинхрон часов/файлы в ту же секунду; игнор `Cache-Control`/`Vary`; дорогой хеш на каждый запрос вместо дешёвой метки. Часто оба заголовка вместе: ETag точнее, Last-Modified — запасной путь.


### сильная — `anthropic/claude-opus-5`

<sub>648 ток., 1.6 с, finish_reason: `stop`, слов: 194, уникальных: 75%</sub>

> **Last-Modified / If-Modified-Since** — валидация по времени изменения. Точность до секунды, слабая семантика: сервер отвечает 304, если ресурс не менялся с указанной даты.
> 
> **ETag / If-None-Match** — валидация по «отпечатку» содержимого. Точнее: ловит изменения внутри одной секунды и откаты к прежнему содержимому; strong ETag (`"abc"`) годится для Range-запросов и условной записи (`If-Match`), weak (`W/"abc"`) — только для кэша.
> 
> **Когда что:**
> - Статика с файловой системы — Last-Modified достаточно и дешевле.
> - Динамика, API, JSON — ETag (хеш тела или версия сущности).
> - Оптимистичные блокировки (`If-Match` при PUT/PATCH) — только ETag.
> - На практике отдают оба: клиент сам выберет, прокси получат запас надёжности.
> 
> **Типичные ошибки:**
> - ETag зависит от inode/mtime → на кластере серверов значения расходятся, кэш промахивается.
> - Хеш считается по несжатому телу, а отдаётся gzip/br без учёта кодировки → битые ответы в промежуточных кэшах; нужен `Vary: Accept-Encoding` и разные ETag на варианты.
> - Игнорируют `If-None-Match` при наличии `If-Modified-Since` (по RFC приоритет у ETag).
> - В 304 забывают повторить актуальные валидаторы и `Cache-Control`.
> - Считают ETag заменой `Cache-Control`: без него всё равно летит запрос на валидацию.
> - Утечка приватных данных: ETag как трекинг-идентификатор пользователя.
> - Пересчёт тяжёлого хеша на каждый запрос вместо хранения версии.

## Что различает ответы
Все три верно передают ядро: Last-Modified — валидация по времени с секундной точностью, ETag — по идентификатору содержимого, оба можно отдавать вместе. Ответ 3 идёт глубже: упоминает условную запись через `If-Match` (оптимистичные блокировки), приоритет `If-None-Match` над `If-Modified-Since` по RFC, проблему ETag-хеша по несжатому телу при отдаче gzip и необходимость `Vary: Accept-Encoding` и разных ETag на варианты, а также необходимость повторять валидаторы и `Cache-Control` в ответе 304. Ответ 2 лаконичнее («слабый ETag при Range», «дорогой хеш вместо дешёвой метки»), но не раскрывает выбор по сценариям так развёрнуто и пропускает `If-Match`. Ответ 1 структурно аккуратен (разделение strong/weak, «лучшая практика — оба заголовка, приоритет клиента за ETag»), но список ошибок неоднороден по качеству.

## Ошибки и слабые места
- Ответ 1: пункт «не обрабатывать 304 на клиенте (повторно парсить пустое тело)» сформулирован косноязычно — реальная проблема в том, чтобы подставлять закэшированное тело, а не в «парсинге пустого». Совет «сильный ETag на динамический HTML — нужен слабый W/» спорен: weak-валидатор не лекарство от микровариаций, а семантика эквивалентных представлений. Нет упоминания `If-Match`, `Vary`, приоритета ETag при двух заголовках.
- Ответ 2: «рассинхрон часов» при Last-Modified — не главная проблема (дату генерирует и сравнивает сервер, перекос часов клиента роли не играет); формулировка расплывчата. Плотность высокая, но за счёт телеграфного стиля часть пунктов («игнор Cache-Control/Vary») названы без объяснения. Нет `If-Match`, нет приоритета ETag при совместной отправке.
- Ответ 3: фактических ошибок не вижу. Объём на грани лимита в 200 слов, но в рамках. «Ловит откаты к прежнему содержимому» верно только при хеше содержимого, что из контекста ответа очевидно.

## Вывод
Лучший — Ответ 3: он один исчерпывает сценарии (условная запись, Range, кодировки, кластеры) и типовые промахи без выдумок. Ответы 1 и 2 годные, но разница в глубине реальная, однако не драматичная (~1–2 балла): для повседневного ответа хватило бы и 1-го, для инженерной практики пригодится 3-й.
