# Temperature Lab (task-4)

Настольное приложение (Tauri + Rust): по кнопке **«Сравнить»** один и тот же
запрос уходит модели три раза — при `temperature` 0, 0.7 и 1.2 — а затем старшая
модель **glm-5.3** разбирает три ответа по точности, креативности и разнообразию
и говорит, какая настройка для каких задач.

Чат из прошлой версии убран полностью: остался только доступ к API, переписанный
с Yolo-Auto на Z.AI.

## Как запустить

Готовый исполняемый файл лежит прямо здесь:

```text
tree/task-4/temperature-lab
```

Его можно открыть обычным двойным кликом — компилировать проект, запускать
скрипты или вручную задавать переменные окружения не нужно. Workaround для
пустого окна WebKitGTK уже встроен в приложение. Для диагностики из терминала:

```sh
./tree/task-4/temperature-lab
```

Исходники и воспроизводимая сборка оставлены для разработчиков. Пересборка из
корня репозитория (ни `tauri-cli`, ни npm не нужны, фронт статический):

```sh
cargo build --release --manifest-path tree/task-4/Cargo.toml
cp tree/task-4/target/release/ask tree/task-4/temperature-lab
```

Дальше: вписать запрос (или взять готовый — «Факты» / «Творчество» / «Код» /
«Идеи»), выбрать провайдера и число прогонов, нажать **«Сравнить»**. Уходит
10 запросов (3 температуры × 3 прогона + разбор + проверка параметра), это
примерно минута; появляются три карточки с метриками и разбор от `glm-5.3`.
Кнопка «Скопировать отчёт» кладёт весь прогон в буфер как markdown.

Ключи берутся из `~/.pi/agent/auth.json` (`zai-coding-cn.key`, `openrouter.key`);
их перебивают `$ZAI_API_KEY` и `$OPENROUTER_API_KEY`.

Терминальный режим — то же самое без окна и без всяких переменных:

```sh
cd tree/task-4
./target/release/ask --cli "запрос" -n 3 --verify -o REPORT.md   # прогон + отчёт в файл
./target/release/ask --verify-temp -p zai                        # только проверка параметра
./target/release/ask --help
```

## Главное, что выяснилось: Z.AI игнорирует `temperature`

Подписочный endpoint Z.AI (`open.bigmodel.cn/api/coding/paas/v4`) **молча
выбрасывает** `temperature`, `top_p` и `do_sample`. Это не догадка, это
воспроизводится за минуту (`ask --verify-temp -p zai`):

| проба | результат |
|---|---|
| `temperature=0`, 6 прогонов | `42, 47, 73, 42, 47, 47` — 3 разных ответа, хотя жадное декодирование обязано дать один |
| `temperature=2.0`, 6 прогонов | тот же разброс, что и при нуле |
| `top_p=0.01`, `do_sample=false` | выдачу тоже не схлопывают |
| связный текст при `temperature=2.0` | не деградирует — при настоящей двойке модель уходила бы в мусор |

### А обычный, не подписочный endpoint даст крутить температуру?

Доказать нельзя, пока на счёте ноль: `open.bigmodel.cn/api/paas/v4` отвечает
`1113 — 余额不足` до того, как что-либо сгенерирует. Но косвенные признаки
сходятся на «да, там параметр должен работать», и вот что удалось выяснить, не
платя:

1. **Подписочный route теряет значение уже после разбора запроса.** Он
   принимает `temperature = -1` и `temperature = 999` — физически невозможные
   величины — и как ни в чём не бывало отвечает нормальным текстом. При этом
   `"temperature": "abc"` он отвергает с `Cannot deserialize value of type
   java.lang.Double`. То есть поле читается на входе и выбрасывается где-то
   между шлюзом и сэмплером; будь оно живым, `-1` обязано было бы упасть.
2. **У обычного route есть слой валидации генерации, которого нет у
   подписочного.** `thinking: {type: disabled}` на `glm-5.3`/`glm-5.3-flash`
   там отклоняется с `1210 — модель всегда думает; используйте low, high или
   max`, а coding-подписка тот же запрос спокойно принимает и выполняет.
   Значит это две разные обработки запроса, а не один бэкенд за двумя URL, и
   упрощена именно подписочная.
3. **Ограничение по рассуждениям на payg жёстче.** Проходит только
   `reasoning_effort: low`; `minimal` и любой `thinking`-объект отклоняются.
   Приложение это уже учитывает (`api.rs::adjust`) — иначе проверка на payg
   падала бы на `1210` ещё до первого прогона.

Осторожная оговорка: на payg `glm-5.3` **нельзя отключить рассуждение
совсем**, а длинная цепочка мыслей сама по себе усредняет финальный текст. Так
что даже при честно работающем параметре эффект температуры там может
выглядеть слабее, чем на llama через OpenRouter.

Когда баланс появится — проверка ровно одна команда, ответ будет
`ПРИМЕНЯЕТСЯ` или `ИГНОРИРУЕТСЯ`, без гадания:

```sh
ZAI_API_KEY_BASE_URL=https://open.bigmodel.cn/api/paas/v4 \
  ./target/release/ask --verify-temp -p zai
```

Сейчас эта команда доходит ровно до стены баланса (`HTTP 429 / 1113`) и ни до
чего раньше — то есть готова к запуску в тот же день.

Поэтому **ответы по умолчанию идут через OpenRouter**, где рычаг работает
честно, а **разбор всё равно делает glm-5.3 из Z.AI**, как и требовалось: на
судью игнор температуры не влияет. Провайдер переключается в окне и флагом `-p`;
на Z.AI приложение работает, но честно вешает красную плашку «параметр
игнорируется, различия ниже ничего не доказывают».

## Почему проверке можно верить

`src/verify.rs` не сравнивает тексты на «похожесть» — так отличить работу
параметра от обычного разброса невозможно. Проверяется причинная сигнатура из
двух половин сразу:

* вопрос с широким, но дискретным ответом («случайное число от 1 до 100»);
* при `temperature = 0` декодирование жадное → **все** прогоны обязаны совпасть;
* при `temperature = 2.0` разброс обязан вырасти.

Вердикт `ПРИМЕНЯЕТСЯ` выдаётся, только когда сошлись обе половины; если
`temperature=0` уже не детерминирована — сразу `ИГНОРИРУЕТСЯ`.

### Ловушка, на которую это ловится

Первый выбранный бэкенд OpenRouter (`deepinfra/turbo`) при `temperature=0`
выдавал **разные** ответы на один и тот же длинный запрос: спекулятивное
декодирование ломает воспроизводимость жадного прохода. Выглядело это ровно как
«температура не работает». Поэтому все прогоны прибиты к одной площадке
(`nebius/fp8`, 4/4 одинаковых ответа) через `provider.order` +
`allow_fallbacks: false`, а `require_parameters: true` не даёт уехать на бэкенд,
который проглотит параметр молча.

## Как меряется «разнообразие»

Не со слов модели-судьи. Каждая температура прогоняется N раз, и между
прогонами считается мера Жаккара по словам: **совпадение прогонов**. Чем ниже,
тем разнообразнее выдача. Плюс доля уникальных слов внутри одного ответа
(лексическое богатство) — это разные вещи, и на реальных данных они расходятся.

## Результаты

Готовые отчёты лежат рядом:

* `REPORT-factual.md` — справочный вопрос, OpenRouter;
* `REPORT-creative.md` — творческая задача, OpenRouter;
* `REPORT-zai.md` — та же творческая задача на Z.AI, с красной плашкой.

Совпадение повторных прогонов (ниже — разнообразнее):

| задача / провайдер | t=0 | t=0.7 | t=1.2 |
|---|---|---|---|
| справочная, OpenRouter | **100%** | 27% | 27% |
| творческая, OpenRouter | **100%** | 18% | 10% |
| творческая, Z.AI | 25% | 20% | 21% |

Первые две строки — то, как выглядит работающий параметр: при нуле вывод
детерминирован до буквы, а любое ненулевое значение сразу обрушивает
повторяемость втрое-вчетверо. Разница между 0.7 и 1.2 на коротких ответах уже
не всегда монотонна (в справочной задаче обе дали 27%) — на такой длине шума
больше, чем сигнала, и честнее сказать это, чем подгонять пример.

Третья строка — как выглядит отсутствие параметра: при нуле уже 25% вместо
100%, и порядка между температурами нет вовсе.

Выводы по применимости — в разделе «Разбор» каждого отчёта, их пишет glm-5.3.
Кратко, и это сходится с замерами:

* **0** — факты, классификация, извлечение данных, тесты, строгий формат: нужна воспроизводимость;
* **0.7** — рабочий режим по умолчанию: диалоги, тексты, баланс стабильности и вариативности;
* **1.2** — брейншторминг и черновики, когда нужно много разных вариантов; факты после этого надо проверять.

## Раскладка

```
src/api.rs       два провайдера (Z.AI, OpenRouter), их квирки, один вызов
src/compare.rs   три ветки параллельно, метрики, промпт судье
src/verify.rs    доказательство, что temperature доезжает до сэмплера
src/report.rs    markdown-отчёт
src/main.rs      команды Tauri + режимы --cli / --verify-temp
ui/              фронт: index.html, style.css, app.js (без сборщика)
tauri.conf.json  окно; frontendDist = ui, withGlobalTauri
```

Сборка не требует `tauri-cli` и npm: фронт статический, `cargo build` собирает
всё сам.

## Заметки по разработке

* `cargo test` (25 тестов) и `cargo clippy --all-targets` должны быть чистыми.
* Правки в `ui/` проверяются в живом окне, а не только компиляцией. На этой
  машине окно поднимается так:
  ```sh
  GDK_BACKEND=x11 DISPLAY=:1 WEBKIT_DISABLE_DMABUF_RENDERER=1 \
  WEBKIT_DISABLE_COMPOSITING_MODE=1 ./target/release/ask
  ```
  Без этих переменных WebKitGTK падает в `Failed to create GBM buffer` и рисует
  пустое окно — на нём уже один раз можно было решить, что фронт сломан.
* WebKitGTK игнорирует цвета у `<select>`, пока не снять `appearance` — иначе
  текст серый по серому.
