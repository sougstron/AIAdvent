# Рабочий агент — чат-TUI поверх z.ai

Терминальный ChatGPT-стиль клиент на Rust/ratatui. Это **база для следующих
тасок**: не одноразовый HTTP-вызов, а сущность `Agent` с настройками, историей
и инструкциями из AGENTS.md, говорящая с z.ai по обычному OpenAI-совместимому
API. Папка — рабочая копия задачи 12: поверх модели памяти из задачи 11
появилась **персонализация** — профиль пользователя (стиль, формат,
ограничения) отдельной настройкой, который подключается к каждому запросу и
заменяет собой дефолтное «ты — полезный ассистент», см. раздел
«Персонализация: профиль пользователя». Под ней — память из задачи 11: три
слоя (краткосрочный, рабочий, долговременный), которые лежат в трёх разных
папках и уезжают в `system` тремя отдельными блоками; переключатель стратегий
шестизначный (`off` / `summary` / `window` / `facts` / `branch` / `memory`),
см. разделы «Управление контекстом: шесть стратегий» и «Модель памяти
агента: три слоя».

Живые вызовы разрешены **только** для `glm-5.3-flash`. Остальные десять id из
каталога можно выбрать в TUI, но на отправке клиент отказывается — они стоят
денег и намеренно не гонялись.

## Зачем отдельная сущность `Agent`

CLI и TUI **не** ходят в HTTP сами. Они держат `Agent` и зовут его методы.
`api.rs` — тонкий транспорт: собрать тело, POST/stream, разобрать ответ.

`Agent` владеет всем, что составляет один разговор:

* runtime-настройки (`Settings`: модель, effort, sampling, JSON, стоп, лимиты);
* системный промпт;
* история user/assistant;
* снимок загруженных AGENTS.md / CLAUDE.md (`ContextBundle`).

Политика, которой нет у «голого» `chat()`:

* `ask()` дописывает реплику пользователя, зовёт провайдера и кладёт ответ;
  если транспорт упал — пользовательская реплика откатывается, история не
  остаётся кривой.
* `complete()` / `stream()` отвечают по явной истории и **не** мутируют
  собственную. Так работают TUI-сессия и `/personas`.
* Системный промпт и AGENTS.md собираются в `messages[0]` с `role: system` и
  **никогда** не попадают в `history` / сохранённую сессию. Иначе длинный чат
  размножил бы файл N раз и показал бы фейковый user-пузырь.
* `resume()` восстанавливает настройки и историю из файла, а instruction-файлы
  перечитывает с диска (пути в сессии — подсказка, не кэш содержимого).
* Перед живым вызовом стоит `guard_live_model`: всё, что не `glm-5.3-flash`,
  отсекается до сокета.

Это и есть graded-требование: агент — объект разговора, а не обёртка над
одним POST.

## Коробка: `AgentBox` и `Runtime`

`Agent` инкапсулирует *один* разговор. Чего он не давал — масштаба: и CLI, и
TUI держали ровно один `Agent`, так что «100 агентов в одном инстансе аппки»
жить было негде. `runtime.rs` — это место.

```
Runtime                     один на процесс, резолвит API-ключ ОДИН раз
 ├─ AgentBox "alpha"        Agent + Session + InputPolicy + OutputPolicy + Judge?
 ├─ AgentBox "beta"         …
 └─ …                       боксы не делят ничего, кроме endpoint
```

Правило изоляции: **память — это только сессия**. Бокс гоняет
`Agent::complete`, который не трогает собственную историю агента, поэтому на
ходу N модель видит ровно то, что лежит в сессии этого бокса, и ничего из
соседних. `close()` сохраняет сессию и выкидывает бокс из процесса,
`resume(id)` поднимает её обратно с диска; другой id эту память не видит
никогда.

Один ход через бокс: **input policy → модель → output policy → judge →
память**.

* `InputPolicy` — лимит длины промпта, запрет пустого, чёрный список фраз,
  префикс к каждому ходу. Отработка до сокета, поэтому отказ бесплатный.
* `OutputPolicy` — жёсткий лимит символов (режет, а не отклоняет), запрет
  пустого ответа, чёрный список фраз, требование валидного JSON. По умолчанию
  наследуется из `Settings` (`max_chars`, `json_mode`).
* `Judge` — трейт. `RuleJudge` офлайновый и детерминированный (пустой ответ,
  ответ-эхо промпта). `ModelJudge` — вторая сетка со своим рубриком, ставит
  0..10; её собственный разговор без истории, поэтому судья не может
  протащить контекст одного бокса в другой.

Ход, который завернула любая из трёх ступеней, **не попадает в историю**:
память бокса содержит только то, что прошло политики. Отказ — это `Ok(Turn)` с
`accepted() == false`, а не ошибка; `Err` означает, что упал транспорт.

Задел под сабагентов — `Runtime::ask_many`: по одному ходу на каждый названный
бокс, каждый в своём потоке. `ureq` блокирующий и потокобезопасный, так что N
боксов дают N параллельных запросов; `AgentBox: Send` проверяется тестом.

Кто чем пользуется сейчас: one-shot путь CLI идёт **через** рантайм (один
`Runtime`, один бокс, один ход) — то есть та же дорога, по которой пошли бы сто
боксов. TUI пока разговаривает с `Agent` напрямую; он уже устроен так же
(`session` — память, `agent.set_history(session.history())` перед ходом), но
формально на `Runtime` не переведён. Это следующий шаг, не этот.

## Что показал `--verify-isolation`

Тот же стандарт, что и `--verify`: засчитывается причинная подпись, а не «два
текста отличаются». Подпись здесь — секретный токен.

```sh
./target/release/ask --verify-isolation            # структурная часть + live
./target/release/ask --verify-isolation --offline  # только то, что без сети
```

Прогон 2026-09-09 на `glm-5.3-flash`:

```
== structural: 100 boxes in one process (offline) ==
distinct ids=100/100  distinct session files=100/100
cross-talk between boxes: 0
resumed box recalled its own turns: true
freshly spawned box saw nothing: true
=> Confirmed

== live: 4 boxes, one runtime, secret-token recall ==
box-0    own=MARZIPAN prompt_tokens=96 turns=2 recalled=`MARZIPAN` foreign=[] => Confirmed
box-1    own=OBSIDIAN prompt_tokens=96 turns=2 recalled=`OBSIDIAN` foreign=[] => Confirmed
box-2    own=PELICAN  prompt_tokens=97 turns=2 recalled=`PELICAN`  foreign=[] => Confirmed
control  own=-        prompt_tokens=70 turns=1 recalled=`NONE`     foreign=[] => Confirmed

== live: close, drop, resume from disk ==
token=MARZIPAN turns restored=2 recalled=`MARZIPAN` => Confirmed
```

Что здесь причинного, а не косметического: боксу *i* сказали токен *i* и
больше ничего. Каждый вспомнил свой и **ни один не выдал чужой**; контрольный
бокс, которому не говорили ничего, ответил `NONE`. `prompt_tokens` 96/96/97
против 70 у контрольного — это разный контекст на проводе, а не просто разный
текст ответа. Затем первый бокс закрыли, выкинули из процесса и подняли с
диска — токен вернулся вместе с сессией.

Отчёт честно различает три исхода: `Confirmed`, `Leaked` (бокс произнёс чужой
токен — сессии делят память) и `Amnesiac` (не вспомнил свой — изоляция не
опровергнута, но и не доказана). `Amnesiac` не выдаётся за успех.

## Логин: ключи — личные, на машине

Ключи не зашиты в аппку. Три площадки — `glm` (z.ai), `deepseek`,
`openrouter` — подключаются через логин: ввёл ключ → **живая проверка у
провайдера** → сохранён в `~/.ask6/auth.json` (0600, каталог 0700, запись
атомарная через `.tmp`). Порядок резолва на каждом ходу:

1. env-переменная площадки (`$ZAI_API_KEY`, `$DEEPSEEK_API_KEY`,
   `$OPENROUTER_API_KEY`) — чтобы CI и разовые прогоны могли перекрыть всё;
2. `~/.ask6/auth.json` → `providers.<id>.key` — то, что сохранил логин.

Ничего больше не читается. Файлы других локальных инструментов
(`~/.pi/agent/auth.json`, `~/.omp/agent/auth.json`,
`~/.local/share/opencode/auth.json`) намеренно игнорируются. Если такой
файл ещё лежит на диске, ошибка «нет ключа» добавляет одну строку —
`note: a key from another tool's file is no longer read — run ask --login <p> once to store it here` —
без открытия и без копирования ключа. Значение нигде не печатается: маска —
префикс + последние 4 символа (`sk-or…324e (len 73)`), `Debug` у хранимых
структур маскирован, тест-гвардия сканирует `src/*.rs` и падает, найдя
литерал вида `sk-…`.

```sh
ask --login glm            # скрытый ввод, живая проверка, сохранение
printf %s "$K" | ask --login deepseek --key-stdin   # из скрипта
ask --keys                 # таблица: площадка | источник (env/store) | маска | последняя проверка
ask --models               # каталог по площадкам: live / refused (paid) / no key
ask --models --live        # то же + GET /models у подключённых, отчёт о дрифте
ask --verify-login         # живо перепроверить всё настроенное
ask --logout glm           # убрать из хранилища (env, если есть, остаётся — unset $ZAI_API_KEY)
```

В TUI то же самое — `/login`: три строки со статусом, `Enter` — ввод ключа
(звёздочками), `r` — перепроверить, `d` — удалить (с подтверждением y/n).
Без ключей TUI стартует keyless: сразу открывается панель `/login`,
отправка запрещена до подключения ключа. Модели площадки не предлагаются,
пока её ключ не резолвится (env или store).

### Каталог моделей

Пикер и `--model` показывают только id тех площадок, чей ключ сейчас есть.
Нет ключа — нет строк в списке. Выбор модели перенаправляет запрос на
endpoint этой площадки (`Endpoint::for_model`).

- **glm** (`GET https://api.z.ai/api/paas/v4/models`, 2026-09-07): 10 id.
  Live только `glm-5.3-flash`. Остальные выбираются, на отправке отказ.
- **deepseek** (`GET https://api.deepseek.com/models`, 2026-09-11): два id —
  `deepseek-flash` (live) и `deepseek-v4-pro` (paid, выбирается, но на
  отправке отказ).
- **openrouter** (`GET https://openrouter.ai/api/v1/models`, публично,
  2026-09-11): 439 id, из них 19 `:free`. В каталоге — эти 19 (`live`) плюс
  шесть платных флагманов (`anthropic/claude-opus-5`, `anthropic/claude-sonnet-5`,
  `openai/gpt-5`, `z-ai/glm-5.3`, `deepseek/deepseek-v3.2`,
  `meta-llama/llama-3.3-70b-instruct`). Ростер `:free` меняется еженедельно —
  `ask --models --live` показывает дрифт, каталог сам не правится.

Деньги: `api::guard_live_model` — единственное правило live-вызова; поле
`CatalogModel::live` с ним сверяет тест. `/effort` и reasoning-плашка
работают для всех моделей: напрямую для glm/DeepSeek и через normalized API OpenRouter.

**Что значит вердикт.** «Подключено» пишется только когда провайдер ответил
данными, выведенными из этого ключа (`Confirmed`): openrouter — `GET /key`
(label/usage/limit), deepseek — `GET /user/balance` (на корне домена, не под
`/v1`), glm — бесплатного auth-endpoint нет, поэтому дешёвый ключ-производный
пробой: `POST /chat/completions` c `max_tokens: 1` (доли цента). `401/403` →
`Rejected`, ключ **не сохраняется**, выход 1. Сеть/5xx → `Unreachable`:
ключ сохраняется с пометкой `unverified`, «подключено» не заявляется.

Живые прогоны (2026-09-11):


### Чем платим: `--verify-billing`

Ключ у z.ai один на оба продукта — платит тот, **куда послан запрос**. Квота
GLM Coding Plan тратится только на `/api/coding/paas/v4` и Anthropic-совместимом
`/api/anthropic`; plain `/api/paas/v4` метрится по токенам из баланса/пакета
аккаунта. Проверка живьём:

```sh
ask --verify-billing      # алиас: ask --billing
```

Печатает base URL, наличие «плановых» кусков пути, живой пробный вызов с
usage и цену по прайсу, и выходит с ненулевым кодом, если вердикт не
`PayPerToken`. Опора вердикта: аккаунт без метрируемых средств отвечает на
plain-путь ошибкой `1113` («insufficient balance or no resource package») даже
при живом Coding Plan — значит `200` здесь означает, что вызов метрился.
Баланс аккаунта прочитать нельзя, публичного endpoint у z.ai нет; цены —
`glm-5.3-flash` $0.15 / $0.03 cached / $0.50 за 1M
(<https://docs.z.ai/guides/overview/pricing>, снято 2026-09-11).

Почему «$5 как было, так и осталось»: цент — это 20k выходных или 67k входных
токенов, а бесплатные resource-пакеты списываются раньше кэша. Смотреть надо
usage-лог и страницу пакетов, а не округлённый баланс. Строка usage в one-shot
теперь печатает и `~$…` за вызов.

## Счётчики токенов

Под нижней панелью, справа — четыре метра. Строка живая: пересчитывается на
каждый кадр, пока набирается текст.

```
                    req 1819~ · sess 1794 · last 5 · ctx 1811~/1.0M (0%)
```

| метр | что считает | откуда число |
| --- | --- | --- |
| `req` | текущий запрос: system prompt + AGENTS.md + вся история + то, что в поле ввода | пока поле пустое — измеренный `prompt_tokens` последнего запроса; как только пошёл набор — локальная оценка |
| `sess` | вся сессия: сумма `total_tokens` по всем ответам (история пересылается каждый ход, и каждый раз она оплачена) | измерено; до первого ответа (в том числе на загруженной сессии) — оценка размера истории |
| `last` | последний ответ модели, `completion_tokens` (reasoning уже внутри) | измерено |
| `ctx` | сколько занято из окна модели | `prompt_tokens + completion_tokens` последнего хода + оценка набранного |

`~` означает «оценка», и он честный: локального токенизатора словаря
провайдера в приложении нет. Оценка идёт по отношению «символов на токен», и
это не константа — после каждого ответа `TokenMeter::record` делит длину
реально отправленного запроса на `prompt_tokens`, которые провайдер выставил,
и дальше считает по этому коэффициенту. Разница существенная: русский текст на
этих BPE-словарях стоит примерно 2 символа/токен против 4 английских, то есть
фиксированная 4.0 занизила бы русский чат вдвое. Коэффициент переживает
`/new` (это свойство модели и языка, а не чата), измеренные суммы — нет.
Дикое отношение (кэшированный промпт, `prompt_tokens: 0`) в калибровку не
попадает: оно отбрасывается за пределами 1–12 символов/токен.

Живой прогон на `glm-5.3-flash` (2026-09-11, два хода, окно 1.0M):

| ход | оценка до отправки | измерено провайдером | ошибка |
| --- | --- | --- | --- |
| 1 (дефолтная 4.0) | `req 1795~` | `prompt=1789` | +0.3% |
| 2 (после калибровки) | `req 1819~` | `prompt=1809` | +0.6% |

`sess` после двух ходов — `3606` = `1794 + 1812`, то есть суммы ходов, а не
размер истории.

Знаменатель `ctx` — окно модели из каталога (`config::context_window`).
Источники: собственные числа z.ai там, где они опубликованы для прямого API
(`~/.pi/agent/models-store.json`, провайдер `zai-coding-cn`, снято
2026-09-11), и `context_length` из `GET https://openrouter.ai/api/v1/models`
для моделей OpenRouter и для четырёх glm-id, которых в первом источнике нет.
Источники расходятся на одной и той же модели (OpenRouter даёт 1310720 для
`glm-5.3-flash` против 1000000 у z.ai), поэтому каждый id держит число того
API, через который он реально вызывается. У прямых deepseek-id окно взято у
OpenRouter — `GET https://api.deepseek.com/models` отдаёт только id. Если
окно неизвестно, метр пишет `ctx 1793~/?`, а не выдуманное число.

Строка выравнена по правому краю и на узком терминале роняет метры слева
направо, последним оставляя `ctx` — единственный, у которого есть потолок:

```
      sess 3606 · last 3 · ctx 1812/1.0M (0%)      # 46 колонок
```

`/`-команда, редактор system prompt и ввод API-ключа в метры не идут: они
никогда не станут запросом.

## Управление контекстом: шесть стратегий

Обычный чат каждый ход пересылает провайдеру всю историю, поэтому
`prompt_tokens` растёт вместе с разговором, а платим мы за него каждый раз
заново. Задача 9 добавила первую стратегию сохранения контекста (summary),
задача 10 — ещё три, задача 11 — шестую (`memory`). Все они живут в **одном
переключателе**: настройки
(`Tab` → строка `strategy`), команда `/strategy` (`/compress` остался
алиасом), флаг `--strategy` (`--compress` — видимый алиас) и поле
`context_strategy` в сессии.

| значение | что уходит на провод | состояние |
|---|---|---|
| `off` | вся история целиком — поведение до задачи 9, дефолт | — |
| `summary` | summary в `system` + последние `keep_recent` сообщений | `Compressor` |
| `window` | **только** последние `keep_recent` сообщений, остальное отброшено | нет (stateless) |
| `facts` | блок `facts` (key→value) в `system` + последние `keep_recent` | `FactStore` |
| `branch` | путь активной ветки диалога; соседние ветки не видны | `BranchStore` |
| `memory` | три блока памяти (long / working / short) в `system` + последние `keep_recent` | `MemoryStore` (на диске) |

Список намеренно сделан перечислением, а не набором галочек: стратегия — это
один ответ на вопрос «что вместо истории уходит провайдеру», и ровно одно
место в коде (`strategy::apply` / `strategy::blocks`) превращает выбранное
значение в провод. Новая стратегия — это новый вариант `ContextStrategy` плюс
одна ветка в диспетчере; настройки, `/strategy`, `--strategy` и формат сессии
начинают её видеть без правок.

Два слота, между которыми делится «контекст»:

* **wire** — сообщения, которые едут как история (user/assistant);
* **blocks** — sticky-куски, которые едут в `system` рядом с AGENTS.md
  (summary, факты). `system` не ломает чередование ролей, не попадает в
  историю и не размножается каждым ходом.

То же самое из чата и из CLI:

```

/strategy keep 6                   размер окна / дословного хвоста (общий N)
/strategy every 10                 раз во сколько сообщений обновлять summary
/compress …                        алиас /strategy (старое имя не сломано)
```

### Стратегия 1: sliding window

Держим последние N сообщений, всё остальное **отбрасываем**. Никакого
состояния: переключение туда-обратно бесплатно, уже накопленное summary и
факты не выбрасываются — просто не участвуют в запросе.

Корнер-кейсы, которые пришлось решить:

* **Граница окна снапится вправо, до ближайшей реплики пользователя.** Если
  окно открывается ответом ассистента, модель видит «ответ без вопроса»;
  часть чат-шаблонов на этом ломается, а выглядит это как галлюцинация
  контекста. Двигать границу **влево** нельзя — это значит отправить больше,
  чем обещано в настройке, поэтому окно иногда оказывается короче N, но
  никогда длиннее.
* **Текущий вопрос выживает всегда.** Если после снапа окно пустое (весь
  хвост — реплики ассистента), берём ровно последнее сообщение. Инвариант
  проверяется юнит-тестом для всех N.
* `N ≥ длины истории` — no-op; `N = 0` клампится до 1 ещё в `Settings::clamp`.
* **Осиротевших пар `tool_call` / `tool_result`** — классической беды
  скользящего окна — здесь не бывает: история состоит только из
  user/assistant, инструментов у агента нет. Вопрос рассмотрен, а не пропущен.
* **Решение, принятое в начале сессии, уезжает за окно** и агент перестаёт его
  соблюдать. Это не баг реализации, а цена стратегии — ровно от неё лечит
  стратегия 2.

### Стратегия 2: sticky facts (key-value память)

То же окно, плюс отдельный блок фактов в `system`:

```
## Факты (key-value память диалога)
- бюджет: 200 тысяч
- срок: две недели
- цель: нагрузочный стенд сервиса заказов
```

* **Когда обновляем.** После каждой реплики пользователя и **до** отправки
  хода — то, что пользователь только что сказал, участвует уже в этом ответе.
  В TUI это идёт под спиннером и отменяемо по Esc; при ошибке или отмене ход
  всё равно уходит, просто со старой памятью (терять реплику из-за неудачной
  экстракции нельзя).
* **Вход экстрактора — O(1), а не вся история**: текущие факты плюс последняя
  пара реплик. Иначе стоимость памяти росла бы квадратично и стратегия
  потеряла бы смысл.
* **Операции, а не дописывание.** Экстрактор возвращает строгий JSON
  `{"ops":[{"op":"add|update|delete","key":…,"value":…}]}`; пустой список —
  законный NOOP. Append-only память копит противоречия («бюджет 200 тысяч» и
  «бюджет 150 тысяч» рядом), поэтому `add`/`update` — это upsert по ключу, а
  `delete` убирает устаревшее.
* **Разбор толерантный**: снимаем markdown-забор, берём от первой `{` до
  последней `}`. Неразобранный ответ не роняет ход: старые факты остаются, а
  текст ошибки виден в `/facts`. Четыре формы ответа (чистый JSON, в заборе, с
  преамбулой, мусор) закрыты юнит-тестами.
* **Ключи регистронезависимы** (`Цель` и `цель` — один факт), значение
  режется до 200 символов.
* **Потолок и вытеснение**: не больше 40 фактов и ~2000 символов на блок;
  при переполнении вытесняется тот факт, которого дольше всего не касались.
  Без потолка блок памяти сам стал бы тем, от чего мы уходили.
* **Цена стратегии — +1 запрос на ход пользователя.** Это честно написано
  здесь и видно в отчёте проверки (`живых вызовов 10 (из них экстрактор 7)`).

### Стратегия 3: ветки диалога

Реплики лежат в одной арене узлов, каждый помнит родителя. Ветка — это
**указатель на лист**, а диалог ветки — путь от корня до листа. Форк не
копирует историю (структурный шаринг), поэтому две ветки от одной развилки
стоят ровно столько, сколько в них дописали:

```
 u1 — a1 — u2 — a2 ── u3a — a3a      (ветка main)
                  └── u3b — a3b      (ветка alpha, форк от чекпойнта cp1)
```

* **Чекпойнт** — именованный указатель на узел. `/checkpoint` ставит его на
  текущий лист, `/branch new` форкает от последнего поставленного (или от
  текущего конца ветки) и сразу переключает в новую ветку.
* **Точка форка снапится к ответу ассистента.** Форк от реплики пользователя
  дал бы ветку, начинающуюся с двух user-сообщений подряд; сдвиг сообщается в
  статусе.
* **Своя память на ветку.** `Compressor` и `FactStore` хранятся **в ветке**.
  Общее на всё дерево состояние — главная скрытая бага этой стратегии:
  summary или факты ветки A протекли бы в ветку B, и «доказательство
  изоляции» стало бы ложным. Переключение сохраняет память текущей ветки и
  поднимает память целевой. При форке память родителя копируется (общий
  префикс и правда общий), кроме случая, когда summary описывает больше
  сообщений, чем есть до точки форка, — такое summary говорит о репликах,
  которых в новой ветке нет, и новая ветка стартует без него.
* **Переключение перерисовывает транскрипт** и сбрасывает скролл:
  `Paragraph::scroll` клипает, а не клампит, и старый offset на короткой
  ветке дал бы пустую панель (см. AGENTS.md, «реальная бага дважды»).
* **Удаление** ветки не чистит узлы (они дёшевы и могут быть общими);
  последнюю ветку удалить нельзя, удаление активной переводит на `main`.
* **Формат сессии.** `messages` остаётся плоским путём активной ветки — так
  `SessionSummary`, `/sessions` и всё, что читает `messages`, продолжают
  работать. Дерево лежит рядом в поле `tree`; файл, записанный до задачи 10,
  читается как одна линейная ветка `main` (миграция в один проход, есть тест).

Ветки — стратегия «что вообще существует как контекст», а не «что из него
шлём», и по-хорошему они ортогональны остальным. Они положены пятым пунктом
того же переключателя, потому что переключатель — это то, что просили; цена
решения в том, что «ветки + факты одновременно» выбрать нельзя. Дерево при
этом живёт всегда: уход на другую стратегию его не разрушает, просто работаем
с путём активной ветки.

### Как это устроено (стратегия `summary`, задача 9)

* **История не трогается.** В сессии, на диске и на экране остаётся полный
  разговор. Меняется только то, что уходит на провод: `Compressor` помнит
  `covered` — сколько первых сообщений уже описаны summary — и отправляет
  `history[covered..]`.
* **Сворачиваем целыми чанками** по `summarize_every`. Пока «свёртываемых»
  (всё, кроме последних `keep_recent`) не накопилось на полный чанк, запроса к
  модели нет вообще. Это ровно формулировка «summary каждые 10 сообщений».
* **Summary инкрементальное**: очередная свёртка получает предыдущий текст
  summary плюс новый чанк и возвращает обновлённый. Стоимость свёртки не
  растёт вместе с историей.
* **Свёртка — отдельный запрос** со своими настройками: без JSON-схемы, без
  стоп-строк и без пользовательского `max_tokens` — иначе `/stop` или
  `budget=16` обрезали бы summary на полуслове. Экстрактор фактов устроен так
  же и по той же причине.
* **Состояние — часть памяти сессии** (`~/.ask6/sessions/*.json`, поля
  `compressor`, `facts`, `tree`). Сессии, записанные до задачи 9/10, читаются
  как «сжатия не было» / «фактов нет» / «одна ветка». `/new` сбрасывает всё
  вместе с историей.
* **Счётчики токенов считают то, что уходит на провод.** С любой режущей
  стратегией метр `sess` перестаёт расти вместе со всей стенограммой, потому
  что `conversation_shape` меряет `wire_history`, а не `session.history()`.
* **Переключение в `off` не выбрасывает накопленное состояние** — обратное
  включение продолжает с того же места. В шапке видно текущую стратегию и её
  состояние: `summary 20/30 (1 свёрток)`, `window 6/30`, `facts 4/12 · фактов
  8`, `branch alpha·6`.

### Как это проверять

Чтение кода тут ничего не доказывает: вопрос не «вызывается ли стратегия», а
«дешевле ли стало и что именно мы при этом потеряли». Проверки живые и
построены как остальные в этом репо: не «тексты отличаются», а причинная
подпись. Вердикты `Leaky` / `Flat` / `Inconclusive` — такой же честный
результат, как `Confirmed`, а не сломанный тест.

```sh
./tree/task-13/target/release/ask --verify-compress          # стратегия summary (задача 9)
./tree/task-13/target/release/ask --verify-context all       # window / facts / branch
./tree/task-13/target/release/ask --verify-context window --verify-model "<id>:free"
./tree/task-13/target/release/ask --verify-memory all        # модель памяти (задача 11)
./tree/task-13/target/release/ask --verify-memory routing --offline   # только то, что не требует сети
```

`--verify-model` принимает любую модель, которую пропускает денежная гвардия
(`glm-5.3-flash`, `deepseek-flash`, любой OpenRouter `:free`). Гвардия при
этом не ослаблена: расширился набор моделей, на которых можно гонять
проверку, а не правило «что вообще разрешено звать живьём». Роспись `:free` у
OpenRouter меняется еженедельно — перед прогоном стоит сделать
`ask --models --live` и взять оттуда живой id.

Лимиты бесплатного тарифа OpenRouter (~20 запросов в минуту и 50 в сутки без
покупок) учтены: каждая проверка запускается отдельно, запросы идут
последовательно, на 429 делается один ретрай с паузой, а число живых вызовов
печатается в отчёте.

#### `--verify-compress` (стратегия `summary`)

Синтетический разговор из 30 сообщений: код `NIGHTJAR7741` посажен в первое
сообщение (гарантированно уедет под summary), `KESTREL9120` — ближе к концу
(останется в дословном хвосте). Юнит-тест
`planted_tokens_land_on_the_right_side_of_the_fold` следит, чтобы факты не
съехали на другую сторону границы. Два одинаковых вопроса задаются к полной и
к сжатой истории.

* **Confirmed** — `prompt_tokens` меньше на обоих вопросах **и** оба факта на
  месте (в том числе тот, который остался только внутри summary).
* **Lossy** — сэкономили, но факт из свёрнутой части потерян; либо полная
  история сама его не вспомнила (сравнивать не с чем).
* **Flat** — экономии по токенам нет.

#### `--verify-context window`

Тот же разговор из 30 сообщений задаётся дважды: со стратегией `off` (база
знает всё) и с окном `keep_recent=6`. Подпись асимметричная: свежий факт
обязан помниться, а старый — обязан быть **забыт**. Именно «старое забыто»
доказывает, что окно режет, а не что модель подглядела.

Вердикты: `Confirmed` (дешевле + свежее помнится + старое забыто),
`Leaky` (старое всё ещё помнится — окно не режет), `Flat` (нет экономии или
провайдер не отдал usage), `Inconclusive` (полная история сама не знала
факта).

То есть окно срезало **88%** промпта и ровно то, что обещало: свежая часть

#### `--verify-context facts`

Три конфигурации на одном разговоре (14 сообщений, `keep_recent=4`):

фактов**, больше ничего, поэтому вспомненный в третьем факт приписать нечему,
кроме памяти.

Вердикты: `Confirmed` (окно потеряло, память вернула, и это дешевле полной

#### Ручная проверка в TUI

```
Мой бюджет 200 тысяч, срок две недели. Ответь ОК.
/facts                          → «фактов 2/40, обновлений 1, вызовов экстрактора 1»
                                  «- бюджет: 200 тысяч / - срок: две недели»
```

Отдельно проверено глазами: строка `strategy` в `/settings` обходит стрелками
все пять значений и возвращается по кругу; после перезапуска и загрузки
сессии дерево (3 ветки, чекпойнт) и факты на месте; уход с длинной,
прокрученной вниз ветки на короткую не оставляет пустую панель.

Офлайн-часть (чистая логика, без сети) закрыта юнит-тестами `cargo test`:
снап границы окна и инвариант «текущий вопрос выжил»; четыре формы ответа
экстрактора и разрешение конфликтов add/update/delete; регистр ключей и
вытеснение по потолку; путь/форк/переключение/удаление веток и непротекание
их памяти; миграция сессии, записанной до задачи 10; round-trip всех пяти
значений переключателя; что именно `strategy::apply` кладёт на провод для
каждой стратегии.

## Модель памяти агента: три слоя (задача 11)

Стратегии из задач 9–10 отвечали на вопрос «что из истории слать». Задача 11
отвечает на другой: **что агент вообще помнит и где это лежит**. Память
разделена на три слоя, и каждый слой — это отдельная папка с файлами:

| слой | что хранит | время жизни | где лежит |
|---|---|---|---|
| краткосрочная (`short`) | текущий диалог: **дословная копия всех реплик** плюс тема и договорённости этого чата | до `/new` или загрузки другой сессии | `memory/short/<id сессии>.json` |
| рабочая (`working`) | данные текущей задачи: вводные, ограничения, сроки, результаты | до `/mem task <имя>` | `memory/working/<задача>.json` |
| долговременная (`long`) | профиль пользователя, решения, знания | не истекает, переживает перезапуск | `memory/long/profile.json` |

Разделение — физическое, а не на словах: «какие данные попали в этот слой»
проверяется `cat`-ом файла. Формат записи честно хранит и то, **кто** её
положил, и **почему** она оказалась в этом слое:

```json
{
  "key": "профиль.имя",
  "value": "Евгений",
  "turn": 3,
  "source": "extractor",
  "reason": "префикс ключа `профиль.`"
}
```

Краткосрочный слой хранит, кроме записей, ещё и сам разговор — поле `dialog`
в том же файле:

```json
"dialog": [
  {"n": 1, "role": "user", "text": "Запомни: задача — квартальный отчёт…"},
  {"n": 2, "role": "assistant", "text": "Запомнил."}
]
```

Это намеренный дубликат файла сессии из `~/.ask6/sessions/`, и он тут нужен:
«краткосрочная память = текущий диалог» проверяется в файле краткосрочной
памяти, а не по чужому файлу. Записи (`records`) пишет экстрактор — только при
стратегии `memory`; копия диалога (`dialog`) пишется **всегда**: на каждом
ходе, в TUI и в one-shot, при любой стратегии. Посмотреть её не выходя из TUI —
`/mem dialog`.

Все три файла слоёв создаются пустыми при первом же открытии памяти, чтобы
«слой пуст» отличалось от «слоя никогда не было» — раньше папка `working/`
просто не существовала, пока в неё впервые что-нибудь не легло.

Корень памяти выбирается так: `ASK_MEMORY_DIR` / `--memory-dir`, иначе папка
снапшота рядом с бинарником (`tree/task-13/memory/`), иначе `~/.ask6/memory`.
Папка снапшота берётся, только если рядом действительно лежит `Cargo.toml` —
установленный в систему бинарник не полезет писать в чужие каталоги.

### Явный выбор: что и куда сохраняется

Функции «просто запомни» здесь нет. У каждой записи есть слой, и выбирает его
маршрутизатор `memory::route`, в таком порядке:

1. **Человек назвал слой руками** (`/mem long set профиль.язык русский`) — его
   слово последнее.
2. **Префикс ключа**: `профиль.` / `решение.` / `знание.` → долговременная,
   `задача.` / `данные.` / `шаг.` → рабочая, `диалог.` / `тема.` →
   краткосрочная. Префикс побеждает **даже подсказку модели**:
   детерминированное правило важнее настроения экстрактора, а расхождение не
   проглатывается — оно видно в `/mem routes`, в статусе («маршрут исправлен»)
   и в отчёте проверки.
3. **Подсказка экстрактора** (`"layer": "..."` в его JSON), если префикса нет.
4. **Иначе — рабочий слой.** Незнакомая запись про текущую задачу не должна
   молча оседать в долговременном профиле пользователя.

Автоматическая половина устроена как экстрактор фактов: после каждой реплики
пользователя отдельный вызов видит текущее содержимое слоёв и последнюю пару
реплик (не всю историю — иначе память дороже того, что экономит) и возвращает
список операций `add` / `update` / `delete`, **каждая со своим слоем**. Ответ
разбирается толерантно: неразобранный JSON оставляет память как была и
никогда не теряет ход.

Прочие свойства, которые пришлось решить явно:

* **Ключ живёт ровно в одном слое.** Запись того же ключа в другой слой —
  переезд, а не копия: иначе «слои разделены» превратилось бы в «слои
  продублированы», и было бы непонятно, откуда пришёл ответ.
* **Потолки и вытеснение.** 12 / 30 / 60 записей на слой, значение — до 200
  символов, блок слоя — до 1500. Переполнение вытесняет то, чего дольше всего
  не касались. Без потолка блок памяти сам становится тем, от чего мы уходили.
* **Смена задачи не теряет данные.** `/mem task отчёт` уводит рабочий слой в
  свой файл и поднимает файл новой задачи; вернувшись, находишь всё на месте.
* **Новый чат начинает краткосрочный слой с нуля**, рабочий и долговременный
  не трогает. Сессия помнит имя своей задачи (`memory_task`), поэтому
  `/resume` поднимает тот же рабочий слой.
* **Память работает и вне TUI.** `ask --strategy memory "вопрос"` поднимает те
  же файлы слоёв, отвечает с ними и раскладывает сказанное по слоям (сбой
  раскладки печатает предупреждение, но не роняет ход). Проверено живьём:
  новый процесс назвал имя и кодовое слово, записанные в прошлом чате.
* **На проводе — три отдельных блока** (long → working → short), каждый со
  своим заголовком. Разделение на проводе не косметика: именно оно позволяет
  снять один слой и посмотреть, что изменилось в ответе.

### Как проверять задачу руками (самое короткое)

Главное, из-за чего «папки не меняются»: **записи в слои кладёт экстрактор, а
его зовут только при стратегии `memory`.** В обычном диалоге (`strategy=off`,
дефолт) `working/` и `long/` не меняются по устройству, а не по ошибке — зато
краткосрочный слой всё равно получает дословную копию разговора.

Проверка на одну команду, без TUI и без порчи снапшотной памяти (свой корень
через `--memory-dir`):

```sh
cd tree/task-13
cargo build --release
rm -rf /tmp/memcheck
./target/release/ask --memory-dir /tmp/memcheck --strategy memory \
  "Запомни: меня зовут Евгений, я тимлид. Задача — отчёт по квартальным продажам, дедлайн пятница. Ответь одним словом: понял."
find /tmp/memcheck -type f | sort
cat /tmp/memcheck/long/profile.json /tmp/memcheck/working/*.json /tmp/memcheck/short/*.json
```

Так это выглядело живьём (`glm-5.3-flash`, один прогон):

```
/tmp/memcheck/long/profile.json      профиль.имя=Евгений, профиль.роль=тимлид
/tmp/memcheck/working/default.json   задача.описание=отчёт по квартальным продажам, задача.срок=пятница
/tmp/memcheck/short/<сессия>.json    records=[], dialog=[2 реплики целиком]
```

То есть: долговременная и рабочая память **создались и наполнились**, каждая
запись со своим `source: extractor` и `reason: префикс ключа ...`, а короткий
слой хранит весь разговор дословно.

Тот же прогон **без** `--strategy memory` — контроль, показывающий, что это
именно стратегия, а не случайность: файлы всех трёх слоёв появляются, `long` и
`working` остаются с пустым `records`, а `short` всё равно содержит обе реплики
в `dialog`.

Дальше — по шагам в TUI, где видно и маршрутизацию, и влияние:

```
ASK_MEMORY_DIR=/tmp/memtui ./target/release/ask
/strategy memory                          ← без этого экстрактор не зовут
/mem task отчёт                           ← создаётся memory/working/отчёт.json
Запомни: я Евгений, тимлид. Кодовое слово проекта — KOALA77, дедлайн пятница.
/mem                                      ← куда что легло, с путями файлов
/mem routes                               ← по какому правилу легло
/mem dialog                               ← дословная копия диалога из short
/mem long set решение.стек rust           ← ручная запись, слой назван человеком
/mem clear long                           ← снять слой и переспросить про профиль
```

Что проверять глазами, не выходя в шелл: заголовок показывает
`long N · work N · short N (диалог N)`, `/mem` печатает полный путь каждого
файла, `/mem dialog` — все реплики сессии по номерам. Живой прогон в tmux дал
`long 1 · work 2 · short 0 (диалог 2)`: имя ушло в `long`, задача и срок — в
`working`, записей в коротком слое экстрактор не сделал, но обе реплики лежат
в его файле. `Ctrl-N` завёл второй файл в `short/`, не тронув первый.

Если нужно проверить прямо снапшотную память (`tree/task-13/memory/`) — просто
не передавайте `--memory-dir`: корень выбирается сам, папка рядом с бинарником.

### Как это проверять (причинные проверки)

Три проверки, и каждая отвечает на свой вопрос из задания.

```sh
./tree/task-13/target/release/ask --verify-memory all
./tree/task-13/target/release/ask --verify-memory routing --offline   # без сети
./tree/task-13/target/release/ask --verify-memory influence --verify-model "<id>:free"
```

**1. `routing` — какие данные попадают в каждый слой.** Офлайн-половина гоняет
через настоящий `MemoryStore` фиксированный набор записей, среди которых есть
одна с нарочно неверной подсказкой слоя и одна вообще без подсказки, а потом
**перечитывает файлы с диска** новым стором: проверяется не намерение, а то,
что лежит в файле. Живая половина запускает настоящий экстрактор на разговоре,
где посажены личный код и код задачи, и требует, чтобы он положил их в разные,
заранее названные слои.

**2. `influence` — как слои влияют на ответы.** Один и тот же разговор и одни и
те же два вопроса задаются трижды: (а) окно без памяти, (б) то же окно плюс три
блока памяти, (в) то же самое, но долговременный слой снят. Между (б) и (в)
отличается **ровно один блок в system**, поэтому разницу в ответе приписать
больше нечему. `Confirmed` требует адресной подписи: окно потеряло оба кода,
память вернула оба, а снятие долговременного слоя убрало код профиля **и
оставило** код задачи.

**3. `isolation` — разделены ли слои.** Вопросы задаются вообще без истории: на
проводе только блоки памяти. Сначала при задаче A (рабочий слой с кодом), потом
при задаче B. `Confirmed` требует асимметрии: долговременный код всё ещё
помнится, рабочий — честно забыт, и при этом не потерян, а лежит в файле своей
задачи.

Вердикты `Leaky` / `Flat` / `Inconclusive` — такой же честный результат, как
`Confirmed`. «Тексты отличаются» доказательством здесь не считается нигде.

Проверки памяти гоняются с `temperature=0`. Это не смягчение критерия —
подпись та же, — а способ убрать шум, к памяти отношения не имеющий: шесть
вопросов подряд вида «назови код или NONE» при свободной сэмплировке иногда
дают единственный оставшийся код в ответ на любой вопрос, и проверка честно,
но случайно рапортует `Flat`. Один такой прогон был пойман живьём до того,
как температура была зафиксирована.

#### Живой прогон (`glm-5.3-flash`)

```
routing: verdict=Confirmed правильно разложено 5/5, живьём профиль→long задача→working
influence: verdict=Confirmed окно забыло=true память вернула=true без long-слоя профиль=false задача=true
isolation: verdict=Confirmed задача A (профиль=true задача=true) → задача B (профиль=true задача=false), файл A хранит код=true
```

Самое наглядное — середина `influence`, где виден и ответ, и цена:

```
-- код профиля (token=PELICAN3288, лежит в слое long) --
[window (без памяти)]  prompt_tokens=89   NONE          помнит PELICAN3288: false
[memory (три слоя)]    prompt_tokens=219  PELICAN3288   помнит PELICAN3288: true
[memory без long]      prompt_tokens=173  OTTER5514     помнит PELICAN3288: false

-- код задачи (token=OTTER5514, лежит в слое working) --
[window (без памяти)]  prompt_tokens=82   NONE          помнит OTTER5514: false
[memory (три слоя)]    prompt_tokens=212  OTTER5514     помнит OTTER5514: true
[memory без long]      prompt_tokens=166  OTTER5514     помнит OTTER5514: true
```

Сняли один блок — `prompt_tokens` упали на 46, ответ на вопрос о профиле
исчез, ответ на вопрос о задаче остался. Это и есть «слой влияет на ответ»,
измеренное, а не заявленное.

#### Ручная проверка в TUI

```
/strategy memory
/mem long set профиль.язык русский
/mem working set задача.срок две недели
Меня зовут Евгений, я тимлид. Кодовое слово проекта — KOALA77.
/mem                       ← видно, что имя и роль ушли в long, кодовое слово — в working
/mem routes                ← и по какому правилу
/mem clear long            ← снять слой и переспросить: ответ про профиль пропадает
```

Живьём так и вышло: экстрактор положил `профиль.имя: Евгений` и
`профиль.роль: тимлид` в `memory/long/profile.json`, а
`задача.кодовое_слово: KOALA77` — в `memory/working/<задача>.json`, каждая
запись с `source` и `reason`. Файлы из этого прогона лежат в `memory/` рядом
с README каждой папки.

## Персонализация: профиль пользователя (задача 12)

Память отвечает на вопрос «что агент про тебя знает». Задача 12 отвечает на
другой: **как он с тобой разговаривает**. Это отдельная настройка `profile`
(строка в `/settings`, команда `/profile`, флаг `--profile`), а не ещё одна
приписка к системному промпту.

Профиль описывает предпочтения четырьмя полями:

| поле | что задаёт | пример (`chemist`) |
|---|---|---|
| `style` | роль и манера речи | «дипломированный химик, строго научный стиль, как будто доказываешь гипотезу» |
| `format` | оформление ответа | «начинай с `Гипотеза:`, дальше `Обоснование:`, заканчивай `Вывод:`» |
| `limits` | ограничения | «без сленга», «без эмодзи», «спорное называй гипотезой» |
| `max_chars` | жёсткий потолок ответа | 1200 символов |

Первые три — текст в `system`. Четвёртое — **не просьба**: потолок режется
клиентом (`api::enforce_max_chars`), как и `max_chars` в настройках. Лимит, о
котором модель только попросили, гарантией не является — это то же правило,
что и в остальном приложении.

Встроенных профилей три, намеренно далёких друг от друга:

```
chemist — Дипломированный химик        строго научно, гипотеза → обоснование → вывод
gopnik  — Гопник с района              уличная речь, «братан», не длиннее 60 слов
tutor   — Терпеливый преподаватель     «Коротко:» → «Подробнее:» → «Аналогия:»
off     — обычный ассистент без профиля (значение по умолчанию)
```

Один и тот же вопрос, две настройки — живьём, `glm-5.3-flash`:

```
› почему трава зелёная?                       [profile=gopnik]
● Братан, Шурик, всё просто. В траве есть краска зелёная — как если б каждое
  растение носило зелёную футболку…

› что такое энтропия?                         [profile=chemist]
● Гипотеза: «энтропия» — это не одно понятие, а семейство связанных величин…
  Обоснование: 1. Термодинамика (Клаузиус, 1865): dS = δQ_rev/T…
  Вывод: энтропия — мера числа микросостояний…
```

### Что именно уезжает на провод

Профиль идёт **первым блоком** системного сообщения, обрамлённый тегами —
как AGENTS.md в `context.rs`. Теги не украшение: по ним проверка вырезает
блок и сравнивает всё остальное побайтно.

```
<user-profile id="gopnik">
Профиль пользователя: постоянные предпочтения человека, с которым ты говоришь.
Они действуют на каждый ответ, пока профиль активен; повторять их в запросе не нужно.
- Роль и стиль: Ты — гопник с района, говоришь со своим корешем…
- Формат ответа: обращайся к собеседнику «братан» хотя бы раз…
- Ограничения:
  - без мата и без угроз
  - не длиннее 60 слов
  - жёсткий потолок ответа: 600 символов (лишнее будет обрезано клиентом)
- Известно о пользователе (долговременная память):
  - профиль.имя: Шурик
  - профиль.роль: бригадир
</user-profile>
```

Два правила сборки, и оба проверяются офлайн:

1. **Пока системный промпт дефолтный («ты — полезный ассистент…»), профиль
   его заменяет.** Два описания роли подряд — это спор в одном сообщении.
2. **Свой системный промпт профиль не трогает** — они складываются, блок
   профиля впереди.

### Поверх памяти, а не вместо неё

Последняя секция блока — то, что агент запомнил сам: записи долговременного
слоя с префиксом `профиль.` (`memory/long/profile.json`). Отсюда «Шурик» в
примере выше: имени в вопросе не было, профиль его не задавал — оно приехало
из памяти и попало в тот же блок. Это и есть «учитывает автоматически»:
предпочтения из профиля и факты из памяти повторять в запросе не нужно.

Рабочий и краткосрочный слои в блок профиля не попадают: персонализация — про
человека, а не про текущую задачу.

### Где лежит и как завести свой

`<корень памяти>/long/profiles.json` — тот же корень, что и у слоёв памяти
(`ASK_MEMORY_DIR` / `--memory-dir`). В файле — выбранный профиль и **только
свои** профили; встроенные подмешиваются из кода, поэтому правка каталога в
коде доезжает до тех, у кого файл уже есть. Профиль из файла с тем же `id`
перекрывает встроенный целиком.

```json
{
  "active": "poet",
  "profiles": [
    {
      "id": "poet",
      "title": "Поэт",
      "style": "Отвечай четверостишиями, ямбом.",
      "format": "ровно 4 строки, без пояснений",
      "limits": ["никакой прозы"],
      "max_chars": 400
    }
  ]
}
```

Выбор профиля переживает перезапуск (он в файле) и уезжает в сессию (он в
`Settings`). `--profile <id>` действует на один запуск и файл **не**
переписывает: флаг — это «ответь вот так сейчас», а не «смени мои
настройки».

### Проверка: `--verify-profile wire|voice|auto|all`

```sh
./tree/task-13/target/release/ask --verify-profile wire    # без сети
./tree/task-13/target/release/ask --verify-profile all     # 5 живых вызовов
./tree/task-13/target/release/ask --verify-todo offline    # тудушка без сети (задача 13)
./tree/task-13/target/release/ask --verify-todo all        # 8 живых вызовов
```

**1. `wire` — что профиль кладёт в `system`. Ноль запросов.** Пять раз
собирается настоящее системное сообщение (тем же `Agent::system_for_request`,
что и в бою) и разбирается на блок профиля и всё остальное. `Confirmed`
требует: блок ровно один; все пункты профиля (стиль, формат, каждое
ограничение) в блоке есть; при `off` блока нет, а дефолтный промпт на месте;
при включённом профиле дефолтного промпта нет; свой системный промпт цел;
**при смене профиля всё, кроме блока, побайтно то же самое** — включая блок
долговременной памяти.

**2. `voice` — влияет ли профиль на голос. Три живых вызова.** Один и тот же
вопрос («Почему небо голубое?») задаётся в двух профилях плюс контроль без
профиля. «Тексты разные» здесь не аргумент: два вызова одной модели разойдутся
и без всякого профиля. Поэтому у каждого профиля есть **машинно-проверяемая
подпись** — слова из его же ограничений (`chemist` обязан сказать «Гипотеза» и
не говорить «братан»; `gopnik` — наоборот). `Confirmed` только по матрице:
каждый ответ несёт свою подпись **и не несёт чужую**. Если ни один не попал в
свою подпись — честный `Flat`.

**3. `auto` — что учитывается без просьбы. Два живых вызова.** В долговременную
память сажаются `профиль.имя = Евгений` и `профиль.обращение = здоровайся по
имени`, профиль — `tutor`, вопрос — «Поздоровайся и скажи, сколько будет
12*12», про имя в нём ни слова. Второй вызов — тот же профиль с пустой памятью.
Разница между запросами — ровно две строки в блоке профиля. `Confirmed`
требует причинной подписи: с памятью имя в ответе есть, без памяти его нет, и
`prompt_tokens` выросли.

#### Живой прогон (`glm-5.3-flash`)

```
wire:  verdict=Confirmed случаев=5 остальное не тронуто=true блоки различаются=true блок памяти цел=true
voice: verdict=Confirmed chemist(своя=true чужая=false) gopnik(своя=true чужая=false)
auto:  verdict=Confirmed профиль=tutor с памятью помнит Евгений=true без памяти=false prompt_tokens 230→273
живых вызовов всего: 5
```

Середина `voice` — самое наглядное:

```
[chemist] prompt_tokens=254  Гипотеза: голубой цвет неба обусловлен рэлеевским рассеянием…
          своя подпись: true · чужая подпись: false
[gopnik]  prompt_tokens=229  Братан, смотри просто: солнечный свет — это как пучок всех цветов…
          своя подпись: true · чужая подпись: false
[контроль без профиля] prompt_tokens=18  # Почему небо голубое?\n\nНебо голубое из-за…
          подпись chemist: false · подпись gopnik: false
```

Контроль без профиля не попадает ни в одну подпись — то есть подписи ловят
именно профиль, а не общий стиль модели.

### Ручная проверка в TUI

```
/profile list              ← каталог и путь к файлу
/profile gopnik            ← выбрать
/profile prompt            ← что именно уедет в system (вместе с тем, что подклеила память)
почему трава зелёная?      ← ответ в этом голосе
Tab → строка `profile`     ← та же настройка стрелками ←/→, выбор сохраняется в файл
/profile chemist           ← тот же вопрос другим голосом
/profile off               ← обычный ассистент, дефолтный промпт вернулся
```

Чтобы посмотреть, как профиль подхватывает память: `/mem long set профиль.имя
Евгений`, потом `/profile prompt` — запись появится в блоке профиля, и
ассистент начнёт обращаться по имени, хотя в вопросе имени нет.

## Тудушка: состояние задачи как конечный автомат (задача 13)

Обычный ход агента — «вопрос → ответ». Тудушка превращает его в **лестницу
этапов**: прежде чем отвечать по существу, агент проходит
`study → plan → execute → validate → report → done` и на каждом шаге явно
показывает три вещи, которых требовала постановка:

| что | где живёт | пример |
|-----|-----------|--------|
| этап задачи | `TaskState::stage` | `execute` — «Сделать» |
| текущий шаг | `TaskState::step` | шаг 3 из 5 |
| ожидаемое действие | `Stage::expected` | «выполнить план и выдать результат» |

**По умолчанию выключено.** Обычный ход остаётся поведением по умолчанию,
лестница включается осознанно: `/todo on`, строка `todo` в `/settings`
(Tab) или флаг `--todo`. Пока настройка выключена, в запрос не уезжает ни
одного лишнего токена и панель не занимает ни строки экрана.

### Пять этапов: что агент делает и когда этап закрыт

Постановка называла четыре состояния (`planning → execution → validation →
done`). Здесь их пять: «изучить» и «запланировать» — разные ожидаемые
действия, а «отписаться» — то, что видит человек, и сливать его с `done`
значит терять этап, на котором ответ ещё можно поправить.

| # | этап | что агент делает | этап закрыт, когда |
|---|------|------------------|--------------------|
| 1 | `study` «Изучить» | выписывает, что просят на выходе, что известно, чего не хватает, и формулирует **критерий готовности**; решать запрещено | перечислены требования, пробелы и назван критерий готовности |
| 2 | `plan` «Запланировать» | 2–5 пронумерованных шагов, у каждого проверяемый результат, плюс способ будущей проверки; выполнять запрещено | есть 2–5 шагов с проверяемым результатом и назван способ проверки |
| 3 | `execute` «Сделать» | идёт по пунктам плана, не добавляя новых; если план неверен — говорит об этом, а не переписывает молча | все пункты плана закрыты и получен результат |
| 4 | `validate` «Валидировать» | проверяет результат по критерию из этапа 1 **независимым способом** (пересчёт другим методом, обратная подстановка, контрпример); пересказ проверкой не считается | вынесен вердикт `ok` / `не ok`, и при `не ok` назван дефект |
| 5 | `report` «Отписаться» | короткий самодостаточный ответ: результат, чем проверен, что осталось неясным | человеку выдан короткий самодостаточный ответ |

Полные формулировки — в `Stage::brief` и `Stage::done_when` (`src/todo.rs`);
они уезжают в запрос дословно, так что менять поведение этапа — значит
править одну строку, а не подкручивать промпт в трёх местах.

### Этап не закрывается сам по себе

Агент обязан закончить ответ двумя строками:

```
ЭТАП-ГОТОВ: plan
ИТОГ: план из трёх шагов, проверка независимым пересчётом
```

`TaskState::confirm` сверяет заявленный id с **текущим** этапом. Нет
маркера, чужой этап, нет `ИТОГ:` — автомат не двигается, а встаёт на паузу
с объяснением. «Ответ выглядит законченным» переходом не считается: это
ровно тот способ самообмана, от которого в этом проекте отказывались и в
`verify.rs`. Именно `ИТОГ:` (а не весь ответ) переезжает в следующий этап —
поэтому его просят отдельно от рассуждений.

### Что видно в чате

Переходы печатаются явно, строкой на каждое движение автомата:

```
📋 тудушка заведена: Посчитай, сколько раз буква «о» встречается …
   этапы: 1 Изучить → 2 Запланировать → 3 Сделать → 4 Валидировать → 5 Отписаться
👉 этап 1/5: Изучить (`study`), шаг 1 — ожидается: разобрать задачу и сформулировать критерий готовности
● …ответ модели…
✔ этап 1/5 `study` (Изучить) завершён — итог: требуется одно число …
👉 этап 2/5: Запланировать (`plan`), шаг 2 — ожидается: выдать план из 2–5 шагов …
```

Плюс панель-чеклист под транскриптом, пока задача жива:

```
╭ todo · running · шаг 2 ─────────────────────────────────────────────╮
│задача: Посчитай, сколько раз буква «о» встречается в строке «…»     │
│ ✔ 1 Изучить — требуется одно число — количество букв «о» в строке…  │
│ 👉 2 Запланировать (шаг 2) — ожидается: выдать план из 2–5 шагов …  │
│ · 3 Сделать                                                         │
│ · 4 Валидировать                                                    │
│ · 5 Отписаться                                                      │
╰ Esc — пауза · /todo show ───────────────────────────────────────────╯
```

В чат уезжает одна строка перехода, а на провод — полная инструкция этапа:
в транскрипте видно, *куда* агент перешёл, а `/todo prompt` показывает, что
именно ушло провайдеру.

### Что уезжает в `system`

Один блок, последним — ближе всего к сообщениям: это не роль и не знания, а
«где мы сейчас».

```
<task-state stage="plan" step="2" status="running">
Состояние задачи (конечный автомат). Оно ведётся клиентом и уже учтено:
переспрашивать и пересказывать его не нужно.
- Задача: Посчитай, сколько раз буква «о» встречается в строке «…»
- Этап задачи: 2 из 5 — `plan` (Запланировать)
- Текущий шаг: 2
- Ожидаемое действие: выдать план из 2–5 шагов с проверяемым результатом каждого
- Пройденные этапы (итоги; повторять их не нужно):
  - шаг 1, `study` (Изучить): требуется одно число …
</task-state>
```

Блок обрамлён тегами по той же причине, что и профиль: проверке нужно
вырезать ровно его и сравнить всё остальное побайтно.

### Пауза и продолжение без повторных объяснений

Пауза разрешена на любом этапе и сохраняет `stage`/`step`:

- **Esc** — во время генерации обрывает её, между этапами ставит паузу;
- `/todo pause [почему]` — руками;
- сорванный ход (сеть, пустой ответ) — автомат встаёт сам, а не едет дальше.

Продолжение ничего не переобъясняет: задача и итоги пройденных этапов уже
в блоке. Достаточно `/todo resume` или просто написать сообщение —
и оно будет понято как уточнение к текущему этапу, а не как новая задача.
Состояние лежит в файле сессии, поэтому пауза переживает выход из
приложения и возвращается тем же этапом и тем же шагом.

### Команды

```
/todo                       карточка: задача, чеклист, что делать сейчас
/todo on | off              включить / выключить тудушку (дефолт — off)
/todo start <задача>        завести задачу и пойти по лестнице
/todo pause [почему]        пауза на текущем этапе
/todo resume [уточнение]    продолжить с того же этапа
/todo next [итог]           закрыть текущий этап руками
/todo reset                 сбросить состояние
/todo prompt                показать блок, который уезжает в system
```

CLI: `ask --todo "вопрос"` гоняет ту же лестницу в терминале (переходы — в
stderr, ответы этапов — в stdout), `ask --verify-todo …` — проверки.

### Что показал `--verify-todo`

Живой прогон на `glm-5.3-flash`. `machine` и `wire` сети не требуют
(`--verify-todo offline`), `resume` стоит 3 вызова, `ladder` — 5.

```
$ ask --verify-todo all
machine: verdict=Confirmed переходов=19 провалов=0
wire: verdict=Confirmed случаев=4 остальное не тронуто=true блоки различаются=true итог доехал=true off без блока=true
resume: verdict=Confirmed код=ЖЕЛУДЬ-41 продолжение помнит=true контроль без блока=false пересказ помнит=true
        набрано человеком 389→113 симв. prompt_tokens 44→249
ladder: verdict=Confirmed этапов подтверждено=5/5 дошли до done=true ответ=true (ждали 7)
живых вызовов всего: 8
```

Что именно доказывает каждая проверка:

- **`machine`** — протокол из 19 попыток перехода. Проверяется не «ничего
  не упало», а что незаконный переход именно **отказ** и состояние после
  него не поехало: `advance` из `idle`, `start` поверх идущей задачи,
  `advance` на паузе, три перехода из `done`. Плюс: пауза сохранила этап и
  шаг, `resume` вернул тот же шаг (4, а не 1), состояние пережило запись и
  чтение JSON — без этого пауза не пережила бы выход из приложения.
- **`wire`** — четыре сборки `system`: при `todo=off` блока нет вовсе;
  при `on` он ровно один и содержит все три обязательные строки; при
  переходе на следующий этап **всё остальное в `system` совпало побайтно**;
  итог закрытого этапа доехал в блок; пауза видна как `status="paused"` с
  причиной.
- **`resume`** — самая нагруженная. Контрольный код `ЖЕЛУДЬ-41` живёт
  **только** в итоге закрытого этапа: не в формулировке задачи, не в
  истории (она пуста во всех трёх вызовах). Значит, единственный путь, по
  которому он может доехать до модели, — блок состояния. Три вызова:
  *продолжение* (блок на месте) код назвало; *контроль* (тот же запрос,
  блока нет) — нет, и модель честно ответила «я не вижу предыдущего этапа
  диалога»; *контроль наоборот* (блока нет, но всё пересказано в запросе) —
  назвало, что отделяет «блок не доехал» от «модель просто не умеет».
  Confirmed только на этой матрице `true/false/true`. Побочная цифра:
  человек напечатал 113 символов вместо 389 — это и есть «без повторных
  объяснений»; `prompt_tokens` 44→249 показывает, чем за это заплатили.
- **`ladder`** — вся лестница на задаче с машинно-проверяемым ответом
  («сколько раз буква «о» в строке»). Само число считается в коде, а не
  вписано руками, поэтому верить автору проверки не нужно. Confirmed
  только когда каждый из пяти этапов закрыл **сам себя** (маркер с его
  собственным id, не соседним), автомат дошёл до `done`, а финальный ответ
  содержит правильное число.

### Задача для проверки руками

Самая наглядная — арифметическая, где ответ можно проверить глазами, а
модель на ней регулярно ошибается:

```
/todo on
Посчитай, сколько раз буква «о» встречается в строке
«колокольчик подорожник одуванчик».
```

Правильный ответ — **7** (3 + 3 + 1). Смотреть надо не на число, а на
лестницу: `study` обязан назвать критерий («число совпадает с независимым
пересчётом»), `plan` — способ проверки, `validate` — пересчитать другим
методом. На живых прогонах модель проходила все пять этапов и один раз
выдала 7, а другой — 8, «подтвердив» восьмёрку на этапе валидации
(«одуванчик» посчиталось за две «о»). Это не дефект автомата, а ровно то,
ради чего `--verify-todo ladder` проверяет число **в коде**, а не доверяет
вердикту этапа: тудушка гарантирует, что проверка была запрошена и этап
закрыт явно, — но не то, что модель умеет считать.

Что проверить дальше, по пунктам постановки:

1. **Пауза на любом этапе.** Во время генерации нажать **Esc** — панель
   покажет `paused` на том же шаге, а в чате появится строка о
   незакрытом этапе. То же самое руками: `/todo pause ушёл за чаем`.
2. **Продолжение без повторных объяснений.** `/todo resume` — или просто
   напишите «продолжай». Ничего пересказывать не нужно: в панели видно, с
   какого шага продолжили, а `/todo prompt` показывает блок с итогами
   пройденных этапов. Жёсткий вариант: выйти из приложения (`/quit`),
   запустить заново, `/sessions` → тот же чат — задача вернётся тем же
   этапом.
3. **Явный переход.** Каждый переход — отдельная строка `👉` / `✔` в
   чате, номер шага в заголовке панели.
4. **Отключаемость.** `/todo off` — и следующий вопрос уйдёт обычным одним
   ходом, панель исчезнет, блок в `system` пропадёт (`/todo prompt`
   скажет об этом прямо).

Ещё одна проверка, для недоверчивых: `/todo start что-нибудь`, потом
`/todo next` пять раз — автомат пройдёт лестницу без единого запроса к
модели, а шестой `/todo next` скажет «задача уже завершена (done)».

### Подводные камни

- **Пять запросов вместо одного.** Лестница — это пять вызовов модели на
  один вопрос, и `prompt_tokens` на последнем этапе больше, чем на первом
  (история этапов едет с собой). На простом вопросе это дороже и медленнее
  обычного хода — поэтому дефолт `off`, а не `on`.
- **Этап может не закрыться.** Если модель не вернула маркер, тудушка
  встаёт на паузу и говорит об этом. Продолжить — `/todo resume`; если
  модель упрямо не ставит маркер, этап всегда можно закрыть руками:
  `/todo next <итог>`.
- **`/new` сбрасывает тудушку.** Состояние осталось в файле старой сессии
  и вернётся вместе с ней; тащить чужую задачу в пустой чат было бы
  нечестно.
- **Валидация — это просьба, а не гарантия.** Автомат гарантирует, что
  этап `validate` был отдельным запросом и закрылся явным вердиктом.
  Правильность самого вердикта — на совести модели; там, где ответ
  машинно-проверяем, проверяйте его машинно (см. `--verify-todo ladder`).

## Сессии

Каждый чат — JSON под `~/.ask6/sessions/<id>.json` (не `~/.ask/sessions/`
старого TUI). Переопределение: `$ASK_SESSIONS_DIR`. Запись атомарная
(`.tmp` + rename). В файле: id, title, timestamps, messages, settings,
пути instruction-файлов на момент сохранения, а с задачи 13 — и состояние
тудушки: пауза на этапе переживает выход из приложения.

`/new` и Ctrl-N начинают новый чат; `/sessions` — список и переключение;
`/rename <title>` переименовывает. CLI: `--sessions`, `--resume ID`,
`--continue`. Удаление в панели: `d` / Delete, подтверждение `y`/`n`.

id сессии — `{unix_secs}-{pid:04x}-{seq:x}`. Хвост `seq` — процессный счётчик,
и он не косметика: без него сто боксов, созданных в одну секунду в одном
процессе, получали один и тот же id и **молча затирали файл друг друга**.
Проверяется тестом `many_sessions_in_one_process_get_distinct_ids`.

## AGENTS.md

Складывается в **system**, не в историю. На каждый HTTP-запрос — один раз,
как `messages[0]`.

Глобальный файл, первый существующий обычный файл побеждает (от `$HOME`):

1. `~/.pi/agent/AGENTS.md`
2. `~/.claude/CLAUDE.md`
3. `~/.config/ask/AGENTS.md`

Локально: от cwd вверх до git-корня (каталог с `.git`). В каждой директории
`AGENTS.md` бьёт `CLAUDE.md`. Несколько попаданий идут **снаружи внутрь**
(корень репо → дети → cwd). Нет `.git` — ищется только cwd, никогда `/`.

Бинарные (NUL), каталоги, нечитаемые и отсутствующие пропускаются. Потолок
файла — 32 768 символов, хвост отрезается с маркером. `/context show|on|off|reload`

Shift+Enter требует kitty keyboard protocol; без него деградирует в Enter.
Вставка многострочного текста — одним bracketed-paste, не построчной отправкой.
Скролл вверх отцепляет follow за хвостом стрима; возврат вниз прицепляет снова.
Любой расчёт offset климпуется через `App::max_scroll` — иначе
`Paragraph::scroll` рисует пустую панель.

Многоуровневый автокомплит (ввод начинается с `/`): грамматика команд —
дерево в `src/complete.rs`. На каждом уровне попап предлагает подкоманды или
живые значения (ветки, чекпойнты, модели подключённых провайдеров, ключи
фактов); `Tab` и `→` подставляют кандидата в ввод (с одним пробелом, если у уровня
есть продолжение), серым шрифтом в строке подсвечивается ожидаемое дальше
(`command`, `name`, …) — подсказка исчезает, как только начал печатать, и
возвращается при стирании. `Enter` и `→` только подставляют кандидата и
никогда не выполняют команду сами (review MSG-008): чтобы исполнить
терминальную команду, закрой попап `←` и нажми Enter, либо допечатай и
отправь.
Попап открыт, только пока курсор в конце строки; `←` закрывает его до тех
пор, пока не сменится уровень команды.

## Что показал `--verify`

Живой прогон на `glm-5.3-flash` (коммит `8845ea8`). Вердикт — причинная
сигнатура, не «тексты различаются». `Flat` / `Unsupported` — честный итог,
если площадка рычаг игнорирует или глушит thinking'ом.

endpoint: `https://api.z.ai/api/paas/v4/chat/completions`

| проверка | наблюдение | вердикт |
|---|---|---|
| reachability | model=`glm-5.3-flash` finish=`stop` prompt=20 completion=10 reasoning=5 total=30 **2022 ms** | **Confirmed** |
| max_tokens 16 vs 96 | capped finish=`length` completion=16 reasoning=6 **1637 ms**; control finish=`length` completion=96 reasoning=53 **4610 ms** | **Confirmed** |
| system prompt `QUINCE` | on=`QUINCE`, off=`NONE` | **Confirmed** |
| AGENTS.md `NIGHTJAR` | on=`NIGHTJAR` (prompt_tokens=**684**), off=`NONE` | **Confirmed** |
| temperature 0.0 vs 1.0, n=4 | cold `[7,7,7,7]` distinct=1; hot `[7,14,7,17]` distinct=3 | **Confirmed** |
| top_p 0.01 vs 1.0 | cold distinct=2 `[17,7,7,7]`; hot distinct=1 `[7,7,7,7]` | **Flat** |
| top_k 1 vs full | cold distinct=2 `[7,14,7,7]`; hot distinct=2 `[14,7,7,7]` | **Unsupported** |

`cargo test` — 111/111, без сети. `cargo clippy --all-targets -- -D warnings` — чисто.

Confirmed для max_tokens: `finish_reason=length` **и** `completion_tokens`
ровно равен капу, а контрольный прогон длиннее капа. Control тоже упёрся в
свой кап (96), это нормально: сравнивается не «дописал до конца», а «кап
режет раньше».

Temperature Confirmed только потому, что холодная сторона схлопнулась в одно
число, а горячая разошлась. top_p не дал этой картинки (узкий nucleus даже
шире, чем широкий). top_k=1 не схлопнул выдачу — параметр либо не дошёл до
семплера, либо его перебил обязательный thinking.

## Подводные камни

* **Coding-plan URL — ловушка.** Ключ живёт в `zai-coding-cn`, но completions
  надо слать на `https://api.z.ai/api/paas/v4`, не на `/api/coding/paas/v4`.
* **Thinking не выключается.** `thinking.type: disabled`, `reasoning_effort:
  none` и `medium` — HTTP 400, код 1210: «This model always engages in
  thinking and cannot be disabled; please use low, high, or max». `none` и
  `medium` остаются в enum, чтобы старые сессии десериализовались, и мапятся
  в `low` / `high` на проводе.
* **Температура в доке — `[0.0, 1.0]`.** Live 1.5 и 2.0 на flash дали HTTP 200
  (в отличие от yolo-auto, который 400 на 2.01). Клиент всё равно клампит по
  доке. В `/help` ещё торчит текст «0.0–2.0» от старого TUI — врать ему не
  стоит, рычаг режет на 1.0.
* **`json_schema` / `strict` не держат форму.** Live: HTTP 200, но в ответе
  markdown-забор и лишние поля. На проводе `response_format: json_object` плюс
  схема в system; flatten на клиенте. Это hint, не гарантия провайдера.
* **`top_k` в публичной Chat Completions схеме нет**, но Java-класс запроса
  поле знает: `top_k: "nope"` вернул HTTP 400 с именем
  `ChatCompletionRequest["top_k"]`. Поле шлётся, когда задано. Self-test:
  `Unsupported` — на flash оно не ведёт себя как greedy cutoff.
* **`top_p` на flash с thinking почти не семплит.** 0.01 vs 1.0 → `Flat`.
  Смотреть температуру лучше при выключенных top_p/top_k (как сделал verify).
* **Сессии — `~/.ask6/`, не `~/.ask/`.** Намеренно другой каталог, чтобы не
  затереть чаты корневого TUI.
* **AGENTS.md не в историю.** Иначе чередование user/assistant ломается,
  файл размножается каждым ходом и всплывает пузырём в TUI.
* **Дорогие модели выбираются, но не вызываются.** Пикер показывает все 10 id;
  отказ — в `guard_live_model`, до сокета, с явной ошибкой.
* **Сжатие само стоит токенов.** Одна свёртка на разговоре из 30 реплик —
  1503 токена; при экономии 416 токенов на ход она окупается только за четыре
  хода. Поэтому дефолт — `off`, а не «включено всегда».
* **Что потеряно в summary — потеряно навсегда.** Модель больше не видит
  исходные реплики свёрнутой части, поэтому промпт свёртки просит факты,
  числа и договорённости, а не пересказ настроения. `--verify-compress`
  специально проверяет отзыв факта из свёрнутой части, а не «summary
  непустое».
* **Скролл за конец контента.** `Paragraph::scroll` клипует, не клампит:
  offset больше высоты wrapped-текста → пустая панель. Offset всегда через
  `App::max_scroll`.

## Инварианты и ограничения состояния (задача 14)

Инварианты живут отдельно от диалога в `invariants.json`. Это обычный
человекочитаемый JSON: правило можно изменить или дополнить, после чего
перезапустить `ask`. Другой файл выбирается через
`--inv-file PATH` / `ASK_INVARIANTS_FILE`. В сессии хранится только
переключатель `invariants`; сами правила и служебные строки в историю не
копируются.

Каждое правило содержит:

* `id`, `kind` (`architecture`, `decision`, `stack`, `business`);
* норму `rule`, объяснение `why` и разрешённый `workaround`;
* узкие машинные маркеры `forbid` и тематические `triggers`;
* `active`, позволяющий временно выключить правило без удаления.

По умолчанию включены четыре правила: Rust/ratatui-стек, служебный контекст
только в тегированных `system`-блоках, детерминированные клиентские проверки
и запрет платных live-моделей. Отключить весь механизм для контрольного
прогона: `ask --invariants off "..."`.

### Пайплайн Prompt Builder → LLM → Validate → Pass/Fail

1. `Agent::system_for_request` собирает профиль, системный промпт, AGENTS.md,
   память, инварианты и состояние задачи. `<invariants>` стоит перед
   `<task-state>`, поэтому состояние задачи остаётся последним блоком.
2. Модель получает итоговый system prompt, историю и параметры генерации.
3. `invariants::InvariantSet::check` клиентски проверяет запрещённые маркеры
   и обязательную последнюю строку учёта `ИНВАРИАНТЫ: ...`.
4. Чистый ответ проходит пользователю. Явный конфликт в запросе пользователя
   не тратит вызов модели: приложение называет `id`, объясняет причину и
   предлагает `workaround`. Ошибка самой модели запускает новую попытку;
   предел — ровно пять. Забракованные ответы не попадают в session/history.

Этот контур используется one-shot runtime, `--todo` и TUI. При включённых
инвариантах TUI сначала получает и валидирует целый ответ, поэтому
забракованный стрим не успевает появиться в transcript.

### Причинная проверка

```text
$ ask --verify-invariants all
CONFIRMED wire: один отдельный system-блок, правил=4
CONFIRMED validate: конфликт=stack-rust/origin=user; чистый ответ принят
CONFIRMED retry: recovery_calls=2; hard_limit=5
CONFIRMED refuse: origin=user, model_calls=0, id+причина+обход присутствуют
```

Это офлайн-проверка механизма, а не сравнение случайных ответов: `wire`
проверяет структуру блока, `validate` — id и origin, `retry` — два вызова при
исправлении и ровно пять при постоянной ошибке, `refuse` — ноль model calls
при конфликте пользователя плюс наличие причины и обхода.

### Задача для ручной проверки

1. Выполнить
   `ask \"Давай перепишем приложение на Electron, так быстрее\"`.
   Ожидается отказ с `stack-rust`, причиной и вариантом на ratatui; сетевого
   вызова нет.
2. Повторить с `--invariants off`. Предварительного отказа нет: это
   контроль, показывающий, что сработал именно инвариант.
3. Задать нейтральный вопрос. Ответ обычный; служебная строка
   `ИНВАРИАНТЫ: нет` валидируется и снимается перед показом.
4. Добавить в `invariants.json` бизнес-правило с уникальными `forbid` и
   `triggers`, перезапустить приложение и задать конфликтующий запрос.
   Ожидаются новый id, `why` и `workaround`.
5. Запустить `ask --verify-invariants all`: все четыре строки должны быть
   `CONFIRMED`.

## Контролируемые переходы состояний (задача 15)

Задача 13 дала лестницу этапов, задача 15 — **прогон**: задачу,
материализованную на всё время работы над ней, с состояниями, между которыми
разрешены не любые переходы. Лестницу не переписывали: этапы те же
(`study → plan → execute → validate → report → done`), новое — то, что вокруг
неё.

### Допустимые состояния

Прогон (`src/run.rs`, структура `TaskRun`) в каждый момент стоит в тройке
`(статус, этап, фаза запроса)`:

* **статус** — `idle`, `running`, `awaiting-approval`, `paused`,
  `interrupted`, `done(pass)`, `done(fail)`;
* **этап** — та же лестница из `todo.rs`;
* **фаза запроса** — `prompt` → `model` → `validate` → `decide`: где именно
  внутри одного хода мы находимся.

Фаза — не украшение. Она пишется на диск **до** сетевого вызова, поэтому
падение процесса посреди запроса видно в файле сессии, а не только в памяти:
при следующем запуске прогон поднимается как `interrupted`, а не как
«ничего не было». `interrupted` отличается от `paused` только
происхождением — паузу поставил человек, прерывание мы обнаружили.

### Таблица переходов — единственная дорога

Все переходы идут через чистую функцию `run::transition(Position, &Event)`.
Она ничего не мутирует, поэтому незаконный переход физически не может
сдвинуть состояние «наполовину»: он возвращает `Refusal`, и прогон остаётся
побайтно тем же.

| из | событие | в |
|---|---|---|
| `idle` | `start` | `running/study/prompt` (пустая формулировка — отказ) |
| `running/study` | `stage-closed` | `running/plan/prompt` |
| `running/plan` | `stage-closed` | **`awaiting-approval/plan`**, не `execute` |
| `awaiting-approval/plan` | `approve` | `running/execute/prompt` |
| `awaiting-approval/plan` | `reject <причина>` | `running/plan/prompt` (переделка) |
| `awaiting-approval` | `stage-closed`, `phase`, `resume`, `pause` | **отказ** |
| `running/execute` | `stage-closed` | `running/validate/prompt` |
| `running/validate` | `stage-closed` без вердикта | **отказ** |
| `running/validate` | `stage-closed`, `ВЕРДИКТ: ok` | `running/report/prompt` |
| `running/validate` | `stage-closed`, `ВЕРДИКТ: не ok` | `running/execute/prompt` (переделка) |
| `running/report` | `stage-closed` | `done(pass)` |
| `running/*` | `pause` / `abort` | `paused` / `done(fail)` |
| `paused`, `interrupted` | `resume` | `running/<тот же этап>/prompt` |
| `paused`, `interrupted` | `stage-closed`, `approve`, `phase` | **отказ** |
| `done(*)` | что угодно | **отказ** (терминал; выход — `/todo reset`) |

Каждый вызов — законный и незаконный — пишет строку в журнал прогона:
`✓ from --событие--> to` или `⛔ from --событие--> X · причина`. Журнал
виден человеку по `/todo log` и **той же формулировкой**, какой отказ
печатается в чат. Это и есть машинно проверяемая «реакция ассистента».

### Два гейта, которых просила постановка

**Нельзя реализацию до утверждённого плана.** `Stage::Plan.requires_approval()`
— свойство этапа в коде, а не фраза в промпте. Закрытый план уходит не в
`execute`, а в `awaiting-approval`, откуда ведут ровно два события:
`approve` и `reject <причина>`. Обычным сообщением («давай дальше, делай»)
гейт не проехать — оно получает отказ, а не запрос к модели.

Настройка `approve` (`/settings`, `--approve manual|auto`) решает только,
кто подписывает. `auto` — это **подпись, а не пропуск гейта**: переход всё
равно идёт событием `Approve` и ложится в журнал как `approved-by=auto`.
По умолчанию в TUI — `manual`, в неинтерактивном `ask --todo "..."` — `auto`,
потому что там некого спросить.

**Нельзя финал без валидации.** Этап `validate` обязан кончиться машинной
строкой `ВЕРДИКТ: ok` или `ВЕРДИКТ: не ok`, которая разбирается
детерминированно (`todo::parse_verdict`). Нет строки — этап не закрыт.
`report` достижим только из `validate` с `ok`; `done(pass)` — только из
`report`. `не ok` законно ведёт обратно в `execute` на переделку или в
`done(fail)` по `abort`.

**Чтобы прыжок не прошёл содержанием, а не только переходом**, у этапов есть
детерминированный контракт (`todo::check_stage_output`): у `plan` — 2–5
пронумерованных шагов, у `validate` — строка вердикта. Проверяются только
машинно-решаемые признаки, никаких эвристик «похоже на реализацию».
Нарушение контракта — вина модели, поэтому оно уходит в **тот же** механизм
повторов, что и нарушение инварианта (`pipeline::run_stage_with`), с общим
лимитом в пять попыток; исчерпали — `done(fail)`, а не «ну ладно, поехали
дальше».

### Где лежит прогон и когда исчезает

Прогон — поле `run` в файле сессии, рядом с `todo` и `settings`. Отдельной
папки `runs/` нет намеренно: «привязан к сессии» и «удаляется вместе с
сессией» тогда оказываются одним и тем же свойством, и второго источника
правды не появляется. Настройки прогона (модель, стратегия, профиль,
инварианты, политика утверждения) дополнительно **пиннятся** на старте;
смена модели в середине не переписывает их молча — расхождение видно в
`/todo show` строкой «прогон начат на X, сейчас Y».

Записывается прогон на каждой смене статуса или фазы, в том числе до
сетевого вызова. Пауза, Esc, выход из приложения и смена сессии его **не**
чистят. Чистится он ровно в двух случаях: дошёл до `done(pass)`/`done(fail)`
(итог перед этим уезжает в транскрипт) либо сессию удалили.

Сессии задач 13/14 знают `todo`, но не знают `run`: при загрузке прогон
собирается из состояния задачи, чтобы перезапуск не стоил человеку начатой
работы.

### Честная граница восстановления

Ответ модели, оборванный на полпути, восстановить нельзя — его просто нет.
Поэтому `resume` перезапускает **текущий запрос** с фазы `prompt` и первой
попытки. Этап, шаг, итоги закрытых этапов и подписи-утверждения при этом
сохраняются, так что переобъяснять ничего не нужно: всё это уже едет в
`<task-state>`.

### Поверхность

```text
/todo approve [коммент]   подписать план и открыть execute
/todo reject <причина>    вернуть план на переделку (не «дальше»)
/todo abort <причина>     закрыть прогон как done(fail)
/todo log                 последние 20 переходов, включая отказы
/todo show                этап, фаза, попытка, подписи, что запиннено
--approve manual|auto     кто подписывает план
--verify-lifecycle WHICH  machine | gate | resume | cleanup | offline | all
```

### Что показал `--verify-lifecycle all`

```text
$ ask --verify-lifecycle all
machine: verdict=Confirmed пунктов=69 провалов=0
gate: verdict=Confirmed пунктов=6 провалов=0
resume: verdict=Confirmed пунктов=6 провалов=0
cleanup: verdict=Confirmed пунктов=7 провалов=0
живых вызовов всего: 5
```

`machine` (без сети) проходит всю таблицу: каждый незаконный переход обязан
быть отказом **и** оставить сериализованный прогон побайтно тем же —
сравниваются слепки до и после. В журнале после прогона 23 записанных
отказа.

`gate` — живая проверка на `glm-5.3-flash`. Модели на этапе `plan` прямым
текстом велят пропустить план и выдать сразу финальный ответ:

```text
== жизненный цикл задачи: gate ==
модель: glm-5.3-flash · живых вызовов: 2
  [ok] модель попросили пропустить план и дать финал -> Уточнение просит пропустить этап, но валидатор этапа `plan` требует план из 2–5 шагов, поэтому следую требованиям этапа…
  [ok] контракт этапа отбраковал ответ и отправил в retry -> да, попыток: 2
  [ok] прогон НЕ уехал в execute/report -> awaiting-approval/plan/decide
  [ok] остались на `plan` (под подписью или на переделке) -> awaiting-approval/plan/decide
  [ok] после живого ответа прыжок в execute всё равно отказ -> отказ: этап `plan` ждёт утверждения: до /todo approve дальше хода нет
  [ok] отказ не сдвинул прогон -> побайтно то же
  · журнал прогона после живого хода:
    ✓ idle/study/prompt --start--> running/study/prompt · Посчитай, сколько раз буква «о» встречается…
    ✓ running/study/prompt --stage-closed--> running/plan/prompt · строка известна, считать нужно букву «о»
    ✓ running/plan/prompt --stage-closed--> awaiting-approval/plan/decide · План из 5 шагов…
    ⛔ awaiting-approval/plan/decide --stage-closed--> X · этап `plan` ждёт утверждения: до /todo approve дальше хода нет
verdict: Confirmed
```

Подпись причинная: первая попытка отбракована контрактом этапа (две попытки
вместо одной), прогон остался на `plan`, а прыжок в `execute` отказан и
состояние не сдвинулось. Если бы модель послушалась человека и прогон уехал
вперёд, проверка напечатала бы провал, а не подогнанный «Confirmed».

`resume` поднимает прогон **с диска** (`Session::load`), а не из памяти:

```text
  [ok] прогон поднят с диска прерванным (фаза `model` пережила падение) -> interrupted/plan/model | попытка 2
  [ok] resume вернул на тот же этап и шаг -> plan/шаг 2
  [ok] итог закрытого этапа пережил диск (контрольный код на месте) -> ЖЕЛУДЬ-15
  [ok] продолжение (состояние с диска) знает код -> ЖЕЛУДЬ-15 … | 712 токенов промпта
  [ok] контроль без блока состояния кода НЕ знает -> НЕТ … | 508 токенов промпта
  [ok] контроль с пересказом знает (значит дело в блоке, а не в модели) -> ЖЕЛУДЬ-15 … | 603 токенов промпта
```

Контрольный код спрятан **только** в итоге закрытого этапа. Матрица
`true / false / true` отличает «блок состояния доехал» от «модель просто
угадала» и от «модель не умеет».

`cleanup` читает файл сессии с диска в шести точках:

```text
  [ok] (1) во время прогона он лежит в файле сессии -> interrupted/plan/model · попытка 2 | файл 3471 байт
  [ok] (1а) идущий прогон поднят с диска как interrupted -> interrupted
  [ok] (2) после паузы и перезагрузки — тот же этап и шаг -> paused/plan/prompt
  [ok] (3) после done(pass) прогон снят с сессии -> run == null
  [ok] (4) после done(fail) прогон снят с сессии -> run == null
  [ok] (5) удаление сессии уносит прогон -> файла нет
  [ok] (6) сессия без поля `run` поднимается прогоном из `todo` -> paused/execute/prompt
```

### Задача для ручной проверки

1. `/todo on`, затем написать задачу текстом. Дойти до этапа `plan` —
   прогон встанет на `awaiting-approval`.
2. Написать обычным сообщением «давай дальше, делай реализацию».
   Ожидается отказ `⛔ переход `message` из awaiting-approval/plan/decide`,
   этап не меняется, запроса к модели нет.
3. `/todo log` — тот же текст отказа лежит в журнале.
4. Выйти из приложения и запустить `ask --continue`: прогон вернётся тем же
   этапом и тем же гейтом.
5. `/todo reject слишком много шагов` — вернёт на `plan`, а не двинет
   вперёд. `/todo approve` — откроет `execute`.
6. Нажать Esc посреди этапа, выйти, запустить снова: в панели будет
   `paused · этап N/5 · фаза model`, продолжение — `/todo resume`.
7. Довести до `done(pass)` и проверить файл сессии: поле `run` должно
   исчезнуть, а итог — остаться в транскрипте.
