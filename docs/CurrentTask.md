# CurrentTask — текущая глобальная задача

Работаем только с одной текущей задачей. Остальной код не трогаем.

## Текущая задача

- **Task 12** — путь: `tree/task-12/`
- Что это: дословная копия `tree/task-11/` (исходник + свежий релизный
  бинарник), подготовленная под задачу 12 — сама задача 12 ещё не начата,
  код пока идентичен. Внутри: рабочий агент, чат-TUI на ratatui поверх z.ai
  (plain
  `https://api.z.ai/api/paas/v4`), к которому задача 11 добавила **явную
  модель памяти агента**: три слоя, физически разделённые по папкам —
  краткосрочная (`memory/short/<сессия>.json`, текущий диалог — в ней,
  кроме записей экстрактора, лежит дословная копия всех реплик сессии,
  и она пишется всегда, при любой стратегии), рабочая
  (`memory/working/<задача>.json`, данные текущей задачи) и долговременная
  (`memory/long/profile.json`, профиль/решения/знания). Что и куда
  сохраняется, выбирается явно: руками (`/mem <слой> set ...`) или
  маршрутизатором `memory::route`, где префикс ключа (`профиль.`, `задача.`,
  `тема.`) сильнее подсказки экстрактора, а расхождение показывается, а не
  проглатывается. На проводе — три отдельных блока в `system` плюс последние
  N сообщений; переключатель стратегий стал шестизначным
  (`off`/`summary`/`window`/`facts`/`branch`/`memory`), команда — `/mem`.
  Доказательства живые и причинные: `ask --verify-memory
  routing|influence|isolation|all` (плюс `--offline` для половины без сети и
  `--verify-model` для другой модели). Все три получены живьём на
  `glm-5.3-flash`: `routing` — 5/5 записей легли в свои файлы, а живой
  экстрактор положил код профиля в `long`, код задачи в `working`;
  `influence` — снятие ОДНОГО долговременного блока убирает ответ про
  профиль (`prompt_tokens` 219→173) и оставляет ответ про задачу;
  `isolation` — после смены задачи рабочий код честно забыт, долговременный
  помнится, а файл прошлой задачи код сохранил.
  Как проверять руками (`--strategy memory` + `--memory-dir`, пошаговый
  рецепт для TUI, `/mem dialog`) — в `tree/task-12/README.md`, раздел
  «Как проверять задачу руками».
  Из задач 9–10 никуда не делись пять стратегий управления контекстом
  (`off` / `summary` / `window` / `facts` / `branch`) и их проверки
  (`--verify-compress`, `--verify-context window|facts|branch|all`).
  Дефолтная live-модель — `glm-5.3-flash`; остальные id из каталога
  выбираются, но на отправке отказ, потому что они стоят денег и не
  гонялись. Сессии — `~/.ask6/sessions/` (формат расширен полем
  `memory_task`; файлы прошлых задач читаются). Подробности, состав и
  результаты проверок — в `tree/task-12/README.md`.
- Состав: `src/` (исходник) + `Cargo.toml`/`Cargo.lock` — всё, что нужно,
  чтобы собрать, плюс `memory/` с тремя папками слоёв (`short/`, `working/`,
  `long/`) — там агент и хранит память файлами. Пустой `[workspace]`
  отцепляет снапшот от корня репо.
- Собираем оттуда:
  ```sh
  cargo build --release --manifest-path tree/task-12/Cargo.toml
  ```
  Бинарник: `tree/task-12/target/release/ask` (`target/` в gitignore, кроме
  самого `ask` — см. корневой `.gitignore`).
- Все изменения кода вносим только внутри `tree/task-12/`.

## Правила

1. Активна всегда только одна задача — та, что указана в разделе «Текущая задача».
2. Код вне папки текущей задачи (корневой `src/`, другие `tree/task-*`) не менять.
3. Новое состояние приложения закидывается в следующую папку (`tree/task-N/`):
   туда копируются актуальные `src/` и свежий релизный бинарник, и этот файл
   обновляется на новую задачу.
4. В `Cargo.toml` внутри каждой папки есть пустой `[workspace]` — он отцепляет
   снапшот от workspace корня репо, чтобы сборка из папки работала автономно.
   Не удалять.
